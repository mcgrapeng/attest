## 1. 判据表 14 → 17 条

**位置**：`SKILL.md` 的判据表（现标题「一条命令：交付就绪度判定」下面那张），
以及正文里那句「工具掌握的是 **14** 条机械判据的实测状态」。

**新增三行**（列名与顺序与代码里的 `Check` 构造一致）：

| 判据（报告标题） | key | 证据类别 | 怎么测 |
| --- | --- | --- | --- |
| 计划与机器推导对齐 | `plan-alignment` | 静态 | 判定点从**源码反推**出来，与计划的「DP ID」列**双向**对账：机器有而计划没有 ⇒ 报红；计划有而机器推不出 ⇒ 只列清单待人签；DP ID 指的文件不在仓库里 ⇒ 报红；不变式的钉不直接引用目标模块 ⇒ 报红（`--plan`） |
| 应有判定点覆盖到位 | `decision-coverage` | 静态 | 计划里每条**高危**判定点（error-path / resource / drop / state）都有归属的不变式**或**写清楚的豁免理由；落点 `文件::用例名` 真的存在（`--plan`）。**这条永远不产生「通过」** —— 静态信号不能单独支撑通过 |
| 钉有区分力 | `pin-discriminating` | 实测 | 把源码在钉的位置**改坏**，跑钉住的那个用例：红了 ⇒ 这条钉杀得死这类缺陷；还绿 ⇒ **这条钉发现不了这类缺陷**（`--plan` + `--discriminating`） |

**默认状态（不给 `--plan` 时）**：三条一律 **skipped（未实测）**，证据类别 `untested`。
不要写成「通过」或「无问题」。

**代码依据**：`skills/attest/scripts/readiness.py:3498`（`check_plan_alignment`）、
`:3556`（`check_decision_coverage`）、`:3621`（`check_pin_discriminating`）。

**顺带**：判据总数在正文两处出现（表格上方那句「每条判据要么有实测证据…」附近，
以及「为什么不是『能不能交付』」那段的「14 条机械判据」）—— 两处都要改成 17。

## 2. 输出契约新增「判定点覆盖」一节

**位置**：`SKILL.md` 的「## 输出契约：证据清单，不是裁决」。

现在那张节表是「已实测 / 静态信号 / 未实测 / 本工具不判定」四节。判定点引擎**另起
一节**，不塞进这四节里：

| 节 | 里面是什么 |
| --- | --- |
| 判定点覆盖 | 从源码反推出的判定点，与计划清单对账的结果：总数 / 已归属 / 豁免 / 缺口；高危四类各缺几条；缺口清单；**推导等级**（L3 / L2）；**区分力自证**的已判条数与杀得死条数 |

**这一节为什么单列**：它是**双向对账**的产物，既不是纯实测也不是纯静态 —— 里面既有
机器推出来的东西，也有人写的东西。

**样例（真实运行的输出，逐字）**：

```
── 判定点覆盖 ────────────────────────────────
  判定点总数 2 ｜ 已归属 1 ｜ 豁免 0 ｜ 缺口 1
  高危四类缺口：drop 0 ｜ error-path 0 ｜ resource 1 ｜ state 0
  缺口清单（只列高危档）：
    src/a.ts#closeClient#resource  既没有归属不变式，也没有豁免理由
  推导等级 L3（后端 B2，来源 global-npm）
  区分力自证：1/1 条（100%），杀得死 1 条
```

**要点**：缺口那一行是关键 —— 一个高危判定点，**没有不变式认领它，也没有豁免理由
解释它**。「区分力自证」必须写出**已判条数 / 总条数**（不是只写百分比）—— 自证预算
有限，没判的那些不能被算成「没问题」。

**`--json` 里是三个顶层并列键**：`decision_points` / `alignment` / `discriminating`。
它们**不进 `conclusion`**（结论计数只数 17 条判据的状态）。

**代码依据**：`readiness.py:4010`（JSON 三个并列键）、`:4054` 附近（`── 本工具不判定`
打印处即 `_dpe_print_section` 的落点）。

## 3. 命令行新增四个开关

**位置**：`SKILL.md` 的「## 一条命令：交付就绪度判定」代码块（现只列了
`--plan` / `--include-itest` / `--test-tenant` / `--mutation-check` / `--json`），
以及「## 常用命令」的开关表。

`--plan` 已经在代码里，但 SKILL.md 的开关表里没有它的**降级语义**，要补上。

| 开关 | 默认 | 语义 |
| --- | --- | --- |
| `--plan <文件>` | 无 | 要核对的需求测试计划。**不给它，三条判定点判据一律 skipped（未实测），不是通过** |
| `--discriminating {auto,off,quick,full}` | `auto` | 钉的区分力自证。`auto` = 只对**判定点粒度**的计划跑；`off` = 不跑；`quick` / `full` = 少跑 / 多跑几条（很贵，要复制工作区并多次跑测试） |
| `--analysis-backend {auto,b1,b2,l2}` | `auto` | 判定点怎么推导。`auto` = 有 TypeScript AST 就用（**L3**）；`l2` = 强制只用词法回退（**L2**），此时三条判据**一律降成警告** —— 缺能力绝不报绿 |
| `--lenient` | 关 | 只提醒不阻塞：三条判定点判据的报红一律降成警告 |

**代码依据**：`readiness.py:4178`（`--lenient`）、`:4180`（`--discriminating`）、
`:4184`（`--analysis-backend`）；`--plan` 在 `:4138`。

## 4. 修掉那句过度声称（**这条是 bug，不是措辞**）

**位置**：`SKILL.md` 的「## 反向验证：证明这套判据抓得住东西」末尾。

**现在写的**：

> 它把 `node_modules` / `.venv` **软链**进副本（不复制体积）⇒ 副本里能真跑测试 ⇒
> 反向验证能覆盖**实测类**判据（测试是否绿、覆盖率），不只是静态判据。

**为什么是错的**：现有 `--self-check` 只有两种注入，**两条都是静态判据**：

| 注入 | 期望翻红的判据 | 证据类别 |
| --- | --- | --- |
| `drop-test` —— 清空一个引用了模块导出的测试文件 | 导出的逻辑都有测试（`uncovered-exports`） | **静态** |
| `inject-sleep` —— 往测试里插一个固定等待 | 测试卫生（`hygiene`） | **静态** |

**没有任何一条注入会让「测试是否绿」或「覆盖率」翻红** —— 没有注入能改坏产品代码的
行为，删掉一个测试文件只会让覆盖更少、不会让断言失败。所以「实测类判据从未被证明能红」
是事实，那句话是过度声称。

**改成**：

> 反向验证覆盖**静态**判据（导出的逻辑都有测试、测试卫生）；**实测类判据由缺陷集
> fixture 证明** —— `fixtures/defect-*` 每一条自带一处刻意留下的缺陷与一份钉死的
> 期望判定，实测类判据能不能红由它们回答。

**代码依据**：`skills/attest/scripts/selfcheck.py:43`（`FAULT_KINDS = ("drop-test",
"inject-sleep")`）、`:555`（注入 → 判据的映射）、`:661`。

**注意**：这一条改动会同时出现在 `--self-check-deps` 的说明里 —— 软链依赖让副本能
真跑测试**这件事是真的**，但它只能让「注入后需要跑测试才能观察到的静态判据」判得准，
不能凭空多出实测类判据的注入。

## 5. 「本工具不判定」清单新增两项

**位置**：`SKILL.md` 的「## 输出契约」表格最后一行（现为）：
`需求是否被正确理解 · 产品行为 · 性能 · 安全 · 可用性 · 运维就绪`。

**代码里已经是八项了**（`readiness.py:135` 的 `NOT_JUDGED`），SKILL.md 还是六项。
要改成：

`需求是否被正确理解 · 产品行为 · 性能 · 安全 · 可用性 · 运维就绪 · **并发正确性** · **容量与规模行为**`

**为什么加**：判定点引擎判的是「**有没有**判定点、判点**有没有被**钉住」，不是
「并发下对不对」「扛不扛得住量」—— 后两样本工具没有条件判（没有并发跑、没有压测）。
**列出来是为了不让读报告的人以为「判定点都覆盖了 ⇒ 并发和容量也没问题」。**

**代码依据**：`readiness.py:135-146`。

## 6. 计划格式升级说明（v1 ⇒ v2）

**位置**：`SKILL.md` 的「### 2. 写不变式清单」与「### 4. 核心逻辑细节」两节，
以及「## 常用命令」里 `req_plan.py new` 的说明。

**要写清楚的三件事**：

1. **两种格式**。计划里的「核心逻辑细节」表有两种形态：
   - **v1（旧的模块级维度表）**：维度 / 落点 两列；
   - **v2（判定点粒度表）**：维度 / **DP ID** / 判定点描述 / 归属不变式 / 落点 / 豁免理由 六列。

   格式**不由列数猜** —— 表头里有「DP ID」就是 v2；表头没写但数据行有一列能解析成
   DP ID 也是 v2；都没有才是 v1。

2. **DP ID 的格式**：`文件#锚点#类型`（`src/a.ts#closeClient#resource`）。
   类型取值：`branch` / `boundary` / `error-path` / `resource` / `state` / `drop` /
   `boundary-io` / `concurrency`。**高危四类**是 `error-path` / `resource` / `drop` /
   `state` —— 这四类没有归属不变式也没有豁免理由时**报红**；其余只计数。

3. **升级的降级方向**：**旧格式（v1）不会报错，也不会假装通过** —— 三条新判据一律
   降成**警告**，并在说明里写「本计划还是旧的模块级维度表；升级到判定点粒度后，
   这三条判据才会硬判」。同样地，推导只到 L2（词法回退）时也一律降成警告
   （「判定点推导只到 L2（词法回退）⇒ 这三条判据不硬判（缺能力绝不报绿）」）。

**代码依据**：`skills/attest/scripts/req_plan.py:579`（`detect_plan_format`）、
`readiness.py:3341`（`_dpe_gate`）、`:3307-3311`（两条降级说明的原文）。
