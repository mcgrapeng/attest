## 2. 四把标尺，逐条复评

### 标尺 1：测试是发现缺陷的手段，不是正确性的证明

**上轮判断**：工具输出「结论：达到交付条件 EXIT=0」是方向性误用 —— 实测的是 11 条机械判据，
输出的是对整个模块的裁决，中间的推理层没写在任何地方。

**结论**：**部分关闭**

**证据（关闭的部分）**：

- 裁决措辞已经拆掉。`scripts/readiness.py` 的报告输出现在是
  ```
  结论：0 项阻塞 · 1 项待人工确认 · 5 项无信号 · 1 项实测通过（另有 6 条静态信号）
  ```
  「达到交付条件」「不可交付」这两个词在生产脚本里**已经不存在**（只在回归脚本的断言字符串里出现）。
- 报告尾部固定有一段：
  ```
  ── 本工具不判定 ────────────────────────────────
  需求是否被正确理解 · 产品行为是否正确 · 性能 · 安全 · 可用性 · 运维就绪
  上面只是测试就绪度的实测结果；「能不能交付」仍要人判断。
  ```
  （`scripts/readiness.py:114-121` 的 `NOT_JUDGED` 常量 + 报告分节逻辑。）
- SKILL.md:32-36 明写「它**不是**『能不能交付给客户』的裁决」，
  SKILL.md:176-194 的「输出契约：证据清单，不是裁决」把三档结论与退出码语义写死了。

这一条是上轮哲学审最核心的诉求，它落实得很干净。

**证据（仍开放的部分 —— 而且是同一条标尺的另一面）**：

标尺 1 的完整命题是「**没有发现失败 ≠ 没有缺陷**」。当前实现把这条纪律**只在"零测试"这一种
情形下**执行了；一旦测试文件存在，它就相信「没有发现失败 = 全绿」。

自造样本 `/tmp/g5-jestlike2`（模拟 jest 的失败输出格式 `Tests: 1 failed, 1 passed`）：

```
  ✓ 测试全绿 — 没有失败用例
  — 核心逻辑测试到位 — 测试跑了，但没解析出覆盖率表（runner 可能不支持覆盖率参数）
结论：0 项阻塞 · 1 项待人工确认 · 5 项无信号 · 1 项实测通过
```

**一个明确失败的用例被判为「全绿」。** 原因在 `scripts/readiness.py:432-435`：

```python
def _failed_tests(out: str) -> list[str]:
    """从 node 测试输出里挑出失败的用例名。"""
    return [mm.group(1).strip()
            for mm in re.finditer(r"^not ok \d+ - (.+)$", out, re.M)]
```

只认 TAP 格式。jest / vitest 默认 reporter / mocha spec reporter 都不是 TAP。
**"没有发现失败"在这里是解析失败，不是事实。** 标尺 1 要求的是"证据不足时不要给肯定结论"，
而这里恰恰在证据不足时给了肯定结论。

对照：Python 侧做对了（`/tmp/g5-py-nopytest`）：
```
  — 测试全绿 — 1 个用例 setup 报错（环境/依赖没就绪） —— 不是断言失败，判不了
```
TS 侧没有这条通道。

**补一条**：SKILL.md:42 自己承诺「**只认断言失败**；setup 报错=环境没就绪 ⇒ 未实测」。
样本 A（`node --test test/` 崩溃）拿到的是「✗ 测试全绿 — 1 个用例失败」——
setup 崩溃被算成断言失败。**文档承诺的纪律，实现只在 Python 侧执行。**

> **一句话**：措辞层（输出什么结论）已经对齐标尺 1；证据层（凭什么说全绿）没有。

### 标尺 2：Oracle 问题是测试的中心难题

**上轮判断**：散文层抓住了这一条（`SKILL.md` 的"断言要独立取期望值"），
但工具层完全没有实现 —— 一份期望值取自被测对象输出的测试计划，`check` 照样打绿。

**结论**：**已关闭**

**证据**：

- 新增 `scripts/oracle_check.py`（784 行，stdlib-only），并在 `readiness.py` 里接成
  **第 12 条判据**「断言的期望值独立」（`evidence_kind="static"`，提醒级，不阻塞）。
- 实跑（自造样本 `/tmp/g5-oracle`）：

  合法断言（期望值独立）：
  ```js
  test('legit', () => { assert.equal(add(1,2), 3); });
  ```
  ⇒ 不报。

  同义反复（形态 1，自比较）：
  ```js
  test('selfcmp', () => { assert.equal(add(1,2), add(1,2)); });
  ```
  ```
  src/calc2.test.ts:9  [自比较]  期望值取自被测对象自己的输出 —— 断言恒成立，测不出任何东西
  ```

  形态 2（期望值取自被测对象）：
  ```js
  test('v-left', () => {
    const x = add(1, 2);
    assert.equal(x, add(1, 2));
  });
  ```
  ```
  src/calc3.test.ts:7  [期望值取自被测对象]  期望值取自被测对象自己的输出 —— 等于拿被测对象和自己比
  src/calc3.test.ts:12 [期望值取自被测对象] 期望值取自被测对象自己的输出 —— 等于拿被测对象和自己比
  ```

- **判为提醒不判红，这是对的**。启发式会误报，真问题不能被噪声淹没；
  而且这个工具的读者是工程师，提醒比硬报红更可执行。
- 30 条回归断言在守（`scripts/test_oracle_check.py`，实跑通过）。
- **边界写在脚本 docstring 里**（不是藏在实现里）：只认裸标识符调用、成员调用不认、
  跨文件的期望值传递认不出来、幂等/不变性断言会被报出来需要人逐条驳回。

**一个小漏报**（不影响结论）：`_collect_assignments` 的赋值正则把右侧一路吃到行尾，
写成**单行**（`const x = add(1,2); assert.equal(x, add(1,2));`）时形态 2 漏报。
正常换行的写法能报。属低频边界。

### 标尺 3：覆盖率是代理指标，"这套测试能发现缺陷吗"才是真问题

**上轮判断**：它知道覆盖率是政策问题（SKILL.md 明确写"通用阈值在这里是错的"），
但把覆盖率当核心判据，且缺那把尺子（变异测试）。更尖锐的是：**工具自己也不能证明它能失败** ——
一个交付判定工具如果不能展示"我给你注入一个已知缺陷，你的判据会翻红"，
用户就只能相信它的绿。这把"覆盖率剧场"升级成了"判定剧场"。

**结论**：**部分关闭**

**证据（关闭的部分）**：

- `--self-check` 存在且工作。实跑：
  ```
  $ python3 scripts/readiness.py src --repo fixtures/ts-colocated --self-check
  EXIT=0
    ✔ [drop-test] src/calc.test.ts
        uncovered-exports：pass → fail
        前：2 个运行时导出都有测试引用
        后：2/2 个运行时导出在测试里零引用
    ✔ [inject-sleep] src/calc.test.ts
        hygiene：pass → warn
    结论：反向验证通过
  ```
- 三种结论都实现了（通过 / 未通过 / 没有可注入的故障目标），后两种退出码 1。
- 注入目标是**副本**，不改用户仓库。
- 60 条回归断言在守（`scripts/test_selfcheck.py`，实跑通过）。

**证据（仍开放的部分）**：

**`--self-check` 只证明了两条静态判据能翻红，实测类判据一条都没证明。**

`scripts/selfcheck.py:40-43`：
```python
ID_UNCOVERED_EXPORTS = "uncovered-exports"
ID_HYGIENE = "hygiene"
FAULT_KINDS = ("drop-test", "inject-sleep")
```

`--json` 实测这两条判据的 `evidence_kind`：
```
uncovered-exports → static
hygiene           → static
```

也就是说：反向验证证明的是"**静态判据**抓得住东西"，
没有证明"**我能让『测试全绿』翻红**"。而标尺 3 问的恰恰是后者 ——
"你的测试会失败吗"。当前工具能证明自己会数"零引用"，不能证明自己会数"红"。

`CHANGELOG.md`「修复与已知遗留」自己承认了这一点：
> **自检副本不带 `node_modules`** ⇒ 多数仓库在副本里跑不动测试，`--self-check`
> 证明的是"静态判据抓得住东西"，不是"整套判据（含实测项）抓得住东西"。

这个坦白是诚实的，但它同时说明：**在大多数真实仓库上，`--self-check` 证明不了什么** ——
一个带 `node_modules` 的真实仓库，副本里跑不动测试，于是能翻红的仍然只有那两条静态判据。

**另一处**：`--self-check --json` 的输出里**没有 self-check 段**（`--json` 实测 top keys
只有 `module/tables/checks/conclusion`）—— 反向验证的结果拿不到机器可读形式，
也就是没法进 CI 的证据链。

> **离"判定剧场"远了一步，但还没走出去**：现在能做的是"展示我把一条静态判据弄红了"，
> 不是"展示我把一条实测判据弄红了"。后者才是专家的第一问。

### 标尺 4：Goodhart 定律与"不可自动化的部分"

**上轮判断**（两条）：

1. 工具产出裁决 + 退出码 ⇒ 进 CI 后成为团队目标 ⇒ 团队优化"让工具绿"而不是"让软件对"。
   这是 skill 最大的社会学风险。
2. 有些问题自动化永远答不了；工具诚实地把三条最主观的原则放在"靠人读，不硬编成检查"里，
   但它们在输出里不是一等公民，散落在散文里，报告读者看不到"还有哪些问题本工具答不了"。

**结论**：**部分关闭**

**证据（第 2 条已关闭）**：

- 「本工具不判定」成了**输出里固定的一段**，不是散文里的暗示：
  ```
  ── 本工具不判定 ────────────────────────────────
  需求是否被正确理解 · 产品行为是否正确 · 性能 · 安全 · 可用性 · 运维就绪
  ```
  （`scripts/readiness.py:114-121`，`--json` 的 `conclusion.not_judged` 里也有这六项。）
- SKILL.md:213-221 的「其余三条（靠人读，不硬编成检查）」仍在，且明确标为人的责任。
- SKILL.md:576-577 把「把判据当裁决」列进「常见错法」。

**证据（第 1 条仍开放）**：

Goodhart 的机制没有变：产出裁决 + 退出码 1 ⇒ 进 CI ⇒ 成为目标。
改变的是**裁决的内容**（从"能/不能交付"变成"几个阻塞项"），
这减轻了但没有消除 Goodhart 风险 —— 一个团队仍然可以让"0 阻塞项"变成目标。

不过有一条新事实值得记下：工具现在**不能靠静态信号拿到绿灯**，
退出码 1 的条件是"有阻塞项，**或关键判据（测试是否绿）没测到**"。
这意味着"把工具弄绿"的最短路径是"**真的把测试跑起来并跑绿**"，
而不是"把静态信号调好看" —— 这在结构上把 Goodhart 的压力从"糊弄判据"推向了
"让测试真的存在并真的绿"。**这是缓解，不是消除**：真正的 Goodhart 变形是
"写一批恒真的测试把工具弄绿" —— 而这恰恰是标尺 2 的 oracle 检查在挡的事。

**闭环读法**：标尺 2（oracle 提醒）+ 标尺 3（能失败）+ 标尺 4（不判定清单）
合起来才构成对 Goodhart 的三重防线。当前三道里，标尺 2 与 3 都只关了一半。

## 3. 第三节五条，逐条复评

### 3.1 结论的认知地位错位
**结论**：已关闭
**证据**：SKILL.md:32-36 把头号问题直接写成答案：
「回答的是：**这个模块的交付前提里，哪些已被实测证明、哪些还没被证明、哪些本工具判不了。**」
并紧跟一句「它**不是**『能不能交付给客户』的裁决 —— 需求是否被正确理解、产品行为、性能、

这是上轮哲学审最重的一条，**落实得最彻底**。

### 3.2 证据类别没有分层
**结论**：已关闭
**证据**：`Check.evidence_kind`（`scripts/readiness.py:100-102`）取
`executed` / `static` / `untested`；报告按「已实测 / 静态信号 / 未实测」分三节，
静态信号一节的标题就写着「（不能单独支撑「通过」）」。
`--json` 实测 12 条判据每条都带 `evidence_kind`。
一条正则扫出来的 ✓ 与一次真跑出来的 ✓ 现在在**不同的节**里 ——
证据力差一个量级这件事被显式化了。
另外 `conclusion` 里分了 `measured_pass` 与 `static_signals` 两个计数，
「1 项实测通过（另有 6 条静态信号）」这种话术把两者的份量区分开了。

### 3.3 Oracle 在工具层缺席
**结论**：已关闭
**证据**：见 §2 标尺 2。

### 3.4 需求正确性被判不了
**结论**：已关闭
**证据**：`NOT_JUDGED` 六项固定清单进输出（`scripts/readiness.py:114-121`），

### 4.1 "工具"这一栏：上轮说缺四样，本轮逐样核对

上轮列的四样：变异测试或反向验证、oracle 检查、证据分层、"能失败"的证明。

| 上轮列的缺口 | 本轮状态 |
| --- | --- |
| 变异测试或反向验证 | **有反向验证**（`--self-check`），无变异测试。够不够见 §2 标尺 3。 |

| 证据分层 | **已做**（R4）。 |
| "能失败"的证明 | **部分**：`--self-check` 证明了静态判据能红；实测判据（"测试全绿"）**从未被证明能红**。 |

**关键证据**：TS 车道至今没有"跑不起来 ⇒ 判不了"的通道，
所以它**既不能证明自己会红，也不能在不该红的时候忍住**：

| 情形 | 工具的判 | 应当是 |
| --- | --- | --- |
| 零测试（`/tmp/g5-zero-test`） | 「○ 测试全绿：没有找到任何测试文件」 + EXIT=1 | ✓ 正确 |
| runner 崩溃（`/tmp/g5-std-testdir`） | 「✗ 测试全绿 — 1 个用例失败」 | 应是「未实测（runner 跑不起来）」 |
| 非 TAP runner 失败（`/tmp/g5-jestlike2`） | 「✓ 测试全绿 — 没有失败用例」 | 应是「未实测 / 失败（解析不了 runner 输出）」 |

第二、三行是本轮新发现（详见 `oss-release-review-v2.md` §5.3）。
**"能失败"的证明必须有一个前提：它平时该绿的时候也得真绿、该红的时候也得真红。**
现在第三行说明它在某些 runner 上**平时就是假绿** ——
在这种状态下，反向验证能证明的东西很有限。

### 4.2 "一条命令实测判定能不能交付客户"：目标本身不可达
**结论**：已关闭（**目标表述已修正**）

上轮的论证是：「能不能交付客户」里只有很小一部分是测试可判定的，
一个测试工具能诚实做到的最强命题不是"能/不能交付"，而是：

> **这个模块的交付前提里，哪些已被实测证明、哪些还没被证明、哪些本工具判不了。**

本轮核对：这句话现在就是 SKILL.md:32 的正文，
而且**实现与它逐项对齐**（三档结论 + 证据分节 + 固定不判定清单 + 退出码语义
「有阻塞项，或关键判据（测试是否绿）没测到 ⇒ 1」）。
"目标不可达"这个判断本身仍然成立 —— 但它已经不再是产品缺陷，
因为产品不再声称做那件不可达的事。

**达成度的诚实说法**：上轮给"七成左右"。本轮的复评结论是 ——
**命题表述与输出契约这一层已经到九成以上**（R1/R4 全关、3.1/3.2/3.4 全关）；
**"工具"这一层仍在大约六到七成**（差的是"能失败"的完整证明与 runner 输出解析的健壮性）；
**综合仍在七成上下**，但缺的那三成已经从"目标表述问题"变成了
"两个具体的工程缺陷"（TS 车道的 runner 输出解析、`--self-check` 覆盖不到实测判据）。
这比上轮的说法乐观一档，因为**剩下的是可以修的，不是改不了的**。

## 6. 复评中新发现的问题（哲学层）

### 6.1 标尺 1 的新形态：「没有发现失败」被当成了事实，而不是解析失败

**这是本轮最要紧的哲学层发现。** 详见 §2 标尺 1 的证据。

从哲学上说：上轮批评的是"**没有发现失败**被当成**没有问题**"。
现在这个毛病没有消失，只是**换了个入口** ——
当 runner 的输出格式不是 TAP 时，"没有发现失败"既不是"没有问题"，
也不是"没有失败"，而是"**我根本没读懂 runner 在说什么**"。
工具却把它当成前者报了出去（✓ 测试全绿）。

**为什么这条比 B1 更要紧**：B1 是"没找到测试文件"这种一眼能看出边界的情形，
而且现在有 fixture 守着；这一条发生在**有测试文件、测试文件会被执行**的正常路径上，
覆盖 jest / vitest / mocha —— JS 生态的主流 —— 而且**没有任何 fixture 守着它**
（5 个黄金 fixture 里没有非 TAP runner 的样本）。

### 6.2 标尺 3 的新形态：能失败的证明，在"平时就不该绿"的状态下没有说服力

`--self-check` 的证明力依赖一个前提：**平时该红的时候真的红**。
现在 TS 车道在非 TAP runner 上平时就假绿（§6.1），
于是"我把判据弄红了"这句话在这个状态下说服力有限 ——
用户真正想问的是"我的测试红了，你会不会告诉我"，而答案在 jest/vitest 上是"不会"。

### 6.3 oracle 检查的单行写法漏报（低频）

`_collect_assignments` 的赋值正则吃到行尾 ⇒ 单行写法下形态 2 漏报。
正常换行能报。已在 `oss-release-review-v2.md` §5.6 记录，不影响 R3 的结论。

## 7. 总判定

**NEEDS_WORK_BEFORE_PUBLISH**

### 哲学层一句话

**这个 skill 已经从"判定剧场"里走出了一半。** 输出契约这一侧（R1、R4、3.1、3.2、3.4）
关得很干净：它现在给的是证据清单，边界写在脸上，"交付决策仍归人"这句话在代码里
（`NOT_JUDGED`）而不只是在散文里。上一轮哲学审最核心的那个诉求 —— **不要把"没有发现失败"
当成"没有问题"** —— 在措辞层已经兑现。

**但另一半还留在原地**：证据层。TS 车道仍然把"runner 崩溃"与"解析不了 runner 输出"
分别误判成"用例失败"与"全绿"。这不是措辞问题，是**证据分类问题** ——
它恰好就是标尺 1 本身。而且它发生在最主流的 runner 上。
`--self-check` 也因此只能证明静态判据能红，证明不了"我能让实测判据红"。

### 剩下的三成是什么

| 缺口 | 性质 | 补法 |
| --- | --- | --- |
| TS 车道的 runner 输出分类 | 工程缺陷 | 给 TS 侧补 Python 侧已有的 `setup_errors` 通道；"解析不出任何用例结果 ⇒ 判不了"；失败判定兼容 TAP 之外的格式，或在拿不到可解析结果时拒绝给"全绿"。itest 车道已有现成写法可抄（`summ["tests"] == 0`）。 |
| `--self-check` 覆盖不到实测判据 | 能力缺口 | 给 `--self-check` 加一种注入：**让一条测试真的断言失败**，验证"测试全绿"能翻红。副本要能跑测试（带 `node_modules` 或至少带能跑的依赖）。 |
| Goodhart 风险 | 结构性 | 不可消除。缓解手段已有（静态信号不能单独支撑通过、oracle 提醒、必须真跑测试才能拿到绿灯）。写进 README 的定位里，别假装没有。 |

### 发布定位（沿用上轮的建议，本轮仍然成立）

> 一个把交付前提变成可机读、可核对、可审计的**证据清单**的需求级测试工具。

而不是"判断模块能不能交付"的裁判。
**发布时必须在 README 首屏写明**：只支持 TS/JS/Python；
**runner 输出不是 TAP 格式时，"测试全绿"这条会失真** ——
否则用户会把它当成裁判，而它现在还不是。
