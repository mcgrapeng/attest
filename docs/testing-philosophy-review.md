# 从测试哲学看：发布条件与终极目标达成度

日期：2026-11-14
对象：`req-test-plan` skill
前序：`docs/oss-release-review.md`（工程层面的发布条件评测）

## 一句话结论

**发布条件：还没到**，但差距已收敛成两张可命名的清单（工程 9 条 + 哲学 2 条）。

## 一、测试哲学的四把标尺

### 标尺 1：测试是发现缺陷的手段，不是正确性的证明

Dijkstra 的老话：测试证明缺陷存在，不证明缺陷不存在。绝大多数"覆盖率/质量门禁"工具在
工程上滑向反面用法，把"没有发现失败"当成"没有问题"的证据。

这条标尺下，`readiness.py` 的最终输出

```
结论：达到交付条件     EXIT=0
```

是**方向性误用**。工具实测的是 11 条机械判据的状态，它输出的是对整个模块的裁决。
中间那层推理没有写在任何地方。

不过要公允：CI 需要退出码。所以问题不是"能不能有二元结论"，而是"二元结论的措辞和
它依据的证据类别必须对得上"。这可以修，而且很便宜（见第五节）。

### 标尺 2：Oracle 问题是测试的中心难题

Howden 1968 年提的 "The Oracle Problem"：你凭什么知道这次测试的期望值是多少？
判据来自被测对象自身，就是同义反复（tautology），测试再多也不产生信息。

**这个 skill 的散文层抓住了这一条，而且是整份文档最深的一条**：

> 断言要独立取期望值（从接口/库里读），别用被测对象自己的输出当期望值。
> （`SKILL.md:171-172`）

同类的还有：钉"行为/不变式"而不是实现细节（`SKILL.md:168-169`）、失败要能定位且带
期望值与实际值（`SKILL.md:172-174`）。这三条是资深测试工程师的直觉，写出来不难，
写进工具的规范里很难。

**但工具层完全没有实现它。** `readiness.py` 与 `req_plan.py` 都不检查断言的期望值来自
哪里，也不提示。一份期望值取自被测对象输出的测试计划，`check` 照样打绿。

### 标尺 3：覆盖率是代理指标，"这套测试能发现缺陷吗"才是真问题

Devaney 讲变异测试时说"答案在方差里"：决定可靠性的是测试失败时的分布形态，不是覆盖
了多少行。Barnett 的覆盖率剧场（coverage theater）说的也是这件事。

这个 skill 有两个层次的问题：

1. **它知道覆盖率是政策问题**。SKILL.md:100-103 明确写"通用阈值（行 80）在这里是错的"
   （lumen 的 service 闸阈值是行 49）。这个判断是对的，"门槛归仓库所有"是我见过的对
   覆盖率问题最成熟的处理方式。
2. **但它把覆盖率当核心判据，且没有任何"这套测试能不能发现缺陷"的度量。** 缺的那把
   尺子叫变异测试（mutation testing）：往代码里注入人工缺陷，看你的测试能杀死多少。
   用户要的是"顶级测试开发专家"，而专家的第一个问题是"你的测试会失败吗"，不是"你覆盖
   了多少行"。

更尖锐的是：**工具自己也不能证明它能失败**。一个交付判定工具，如果不能展示"我给你
注入一个已知缺陷，你的判据会翻红"，用户就只能相信它的绿。这把"覆盖率剧场"升级成了
"判定剧场"。

### 标尺 4：Goodhart 定律与"不可自动化的部分"

Goodhart：度量一旦成为目标就不再是好度量。

`readiness.py` 产出一个裁决 + 退出码，这东西会被放进 CI，于是它成为团队的目标。
此时团队优化的是"让工具绿"，不是"让软件对"。这是 skill 最大的社会学风险。

而且它和自己的散文直接冲突：`SKILL.md:76` 写着"一个满屏 ✓ 但其实什么都没测的报告，
比报错更糟"。工具在零测试时产出的正是这样一个满屏 ✓ 的报告（已实跑复现，退出码 0）。

第四条标尺的另一半：有些问题自动化永远答不了（Krieger & Trimble 的探索式测试）。
这个 skill 诚实地把三条最主观的原则放在"靠人读，不硬编成检查"里（`SKILL.md:166-174`），
这是对的判断。但它们在输出里**不是一等公民**，散落在散文里，报告的读者看不到"还有
哪些问题本工具答不了"。

## 二、已经达到的部分

| 维度 | 判断 |
| --- | --- |
| 需求级测试工具包（plan → check → scaffold → 判定闭环） | **达成**。全新仓库实测：骨架可用，`check` 报错分类克制，"钉指向的用例真的存在"是可证伪的硬检查 |
| 测试方法论的散文层 | **接近专家水准**。oracle 独立、行为而非实现、失败可定位、测试隔离与 flaky、门槛归仓库、跑不起来 ≠ 不达标，每条都带 why 和真实数据 |

| 判据的口径纪律（租户口径、生产 vs 测试、skip vs fail） | **成熟**。这是从真实数据里挖出来的，不是设计出来的 |

`SKILL.md` 里的原则部分，我认为是这个 skill 最值钱的东西。问题在于程序层没有把
这些原则兑现。

## 三、没达到的部分（哲学层面，与具体 bug 无关）

### 3.1 结论的认知地位错位

工具掌握的是"11 条机械判据的实测状态"，它输出的是"这个模块能否交付客户"。
这两者之间隔着一整层未言明的推理，而且那层推理里缺的东西比工具能提供的多得多：
需求是否被正确理解、产品行为是否正确、性能、可用性、安全、可运维性、成本可接受性。

哲学上正确的输出是**证据清单**：哪些交付前提已被实测证明、哪些还没被证明、哪些本工具
判不了、哪些只能靠人。把裁决留给有职责的人。

### 3.2 证据类别没有分层

11 条判据里，5 条是纯静态正则或词频分析（测试卫生、具备扩展性、没有重复造轮子、
需求覆盖到位、使用主流开源库），6 条是真跑。报告里它们用同一套 ✓ / ✗ / · / — 记号
排在同一张表里。一条正则扫出来的 ✓ 和一次真跑出来的 ✓，证据力差一个量级，报告没区分。

### 3.3 Oracle 在工具层缺席

散文层要求期望值独立，工具层不检查也不提示。这是原则与实现的最大落差。

### 3.4 需求正确性被判不了

这条必须保留为显式的"本工具不判定"，不能靠散文暗示用户自己记得。作者自己已经认了
（交接文档"未做"节），但在输出契约里它没有位置。

### 3.5 没有反向验证

工具不能证明自己能失败，见标尺 3。

## 四、终极需求目标的达成度

用户的终极目标（按交接文档记录的意图演进）：任意需求在开发时被完整测试工具包驱动，
并能**一条命令、基于实测**判定"这个模块能不能直接交付给客户"；skill 要有"顶级测试
开发专家"的实力。

逐条判：

| 目标 | 达成 | 说明 |
| --- | --- | --- |
| 需求级测试工具包驱动开发 | **达成** | plan / check / scaffold / readiness 闭环，实测可用 |
| 顶级专家的**方法论** | **达成** | 散文层达到，且带真实数据与 why |
| 顶级专家的**工具** | **未达成** | 缺变异测试或反向验证、缺 oracle 检查、缺证据分层、缺"能失败"的证明 |
| 一条命令实测判定"能不能直接交付客户" | **目标本身不可达** | 见下 |

### 为什么最后一条不可达

"能不能交付客户"里，只有很小一部分是测试可判定的：

- 可测：需求的功能性不变式有没有被钉住并被真实用例覆盖、跨存储数据有没有漂、
  测试本身健不健壮、表结构有没有明显缺陷。
- 不可测：需求理解对不对、产品行为对不对、性能、可用性、安全、可运维性、
  客户能不能接受。

一个测试工具能诚实做到的最强命题不是"能"或"不能交付"，而是：

> **这个模块的交付前提里，哪些已被实测证明、哪些还没被证明、哪些本工具判不了。**

这个命题比二元裁决更有用，因为它把决策还给有职责的人，同时又比"我跑了下测试"更有用，
因为它有判据表、有证据类别、有明确的空白清单。

所以终极目标的达成度是七成左右，剩下三成靠改目标表述 + 补四条能力就能补齐，不是靠
把现有代码打磨得更精细。

## 五、最省事的达标路径（哲学层面四条）

这四条加起来不大，但能把"判定剧场"变成"证据工具"。

### R1 输出契约：从裁决改成证据清单，退出码保留

- 报告分两层：**已实测**（带命令、退出码、证据）与**静态信号**（永远不能单独支撑"通过"）。
- 结论三档：**阻塞项 N 项** / **待人工确认 N 项** / **无信号 N 项**；去掉"达到交付条件"。
- 固定一段"**本工具不判定**"清单：需求正确性、性能、安全、可用性、运维就绪。
- 退出码保留（CI 需要），但它对应的是"是否存在阻塞项"，措辞与证据类别一致。

### R2 反向验证：`--self-check`

对目标模块注入一个已知缺陷（改动一行让某条不变式失效），跑一遍判据，展示它翻红。
这是把"我能测你"升级成"我能证明我能测你"。成本远低于完整变异测试，且直击
"你的测试能不能失败"这个专家第一问。

### R3 Oracle 独立性的启发式检查

扫测试文件，标出"期望值取自被测对象自身"的常见形态（断言两侧调用同一模块、
快照自比对、把 SUT 输出当基线）。启发式即可，判提醒不判红。这一条把散文层最深的
原则第一次变成机器检查。

### R4 判据的证据类别显式化

每条判据在代码里带一个 `evidence` 标签（executed / static），报告按标签分节。
顺带把"使用主流开源库"这条空判据一起处理掉：要么实现真判定，要么降级为静态信号。

## 六、发布条件（合并工程与哲学两份清单）

### 工程门槛（`docs/oss-release-review.md` 第十节）

P0 九条：删 `__pycache__` 并加 CI 检查、修零测试假绿、修测试发现作用域、修
`scaffold` 路径穿越、修 `scaffold` 代码注入、scaffold 语言感知、补 LICENSE/README/CHANGELOG、
r3/r4 绝对路径、改写范围声明。

### 哲学门槛（本文新增两条）

- **R1**：输出契约必须是证据清单 + 显式不判定清单，不能是二元裁决。
- **R2**：必须有反向验证能力（`--self-check` 或等价的"能失败"证明）。

### 结论

两条清单都清完即可发布。届时发布的定位应当是：

> 一个把交付前提变成可机读、可核对、可审计的证据清单的需求级测试工具。

而不是"判断模块能不能交付"的裁判。

## 七、方法论备注

- 本文的哲学判断依据的是测试领域公认的概念：测试的证伪立场（`testing shows the
  presence of bugs`）、oracle 问题（Howden 1968）、变异测试与"答案在方差里"
  （Devaney）、覆盖率剧场（Barnett）、探索式测试的边界（Krieger & Trimble）、
  Goodhart 定律。文中未引用具体论文页码，读者可自行核对。
- 本文只做哲学层审视，工程层的可复现证据一律见 `docs/oss-release-review.md`。
