# 三层评测

这个仓库有三层可执行的评测，各管一件事。**不要把它们混为一谈**：
fixture 测工具的判定、eval 测命令的行为、trigger 测 description 会不会被用。

## 1. 黄金 fixture（`fixtures/`）—— 工具的判定对不对

5 个自包含的小仓库，每个钉死一个期望判定：

| fixture | 挡的是哪条质疑 |
| --- | --- |
| `ts-colocated` | 测试发现的作用域（模块内 colocated） |
| `python-repo` | Python 侧的导出引用判据不空转、依赖抽取认得出 |
| `rust-repo` | 认不出的语言要**退出码 2 + 说清**，不是满屏 ✓ |
| `english-reconciler` | 对账脚本输出英文时不得假绿 |
| `no-tests` | 零测试的模块不得被判「达到交付条件」 |

```bash
bash fixtures/run_fixtures.sh
```

退出码：0 全部命中 / 1 有不符 / 3 有 fixture 因环境缺失未判定
（`python-repo` 需要 `pytest` + `pytest-cov`）。

fixture 会被复制到临时目录再跑，不污染仓库。

## 2. 行为 eval（`evals/evals.json`）—— 命令的行为对不对

6 条 eval，每条声明用哪个 fixture 当被测仓库、跑什么命令、断言看命令输出还是产物文件。

断言 DSL：

| 写法 | 含义 |
| --- | --- |
| `exit_code=N` | 退出码必须等于 N |
| `exit_code_any=0\|1` | 退出码在给定集合里 |
| `contains:文本` | 输出里必须出现 |
| `not_contains:文本` | 输出里必须不出现 |
| `any_contains:A\|B\|C` | 至少出现其中一个 |

```bash
python3 evals/run_evals.py            # 跑全部
python3 evals/run_evals.py --only 3   # 只跑某一条
python3 evals/run_evals.py --json     # 机器可读
```

退出码：0 全部通过 / 1 有断言不通过 / 2 没有可跑的 eval。

## 3. 触发评测（`evals/trigger-evals.json`）—— description 会不会被用

20 条查询（10 条该触发 + 10 条近邻不该触发），测的是**模型有没有真的去加载这个
skill**。

```bash
python3 evals/measure_triggers.py                 # 跑全部
python3 evals/measure_triggers.py --max-turns 3   # 给模型几轮
```

**它会调用 `claude -p`，花你自己的额度**（20 条 ≈ 8 美元，取决于模型与轮数）——
所以它不在 CI 里，是发布前手动跑一次的东西。

### 为什么要自己写这个评测器

现成的 skill-creator `run_eval.py` **在这台机器上不可用**：它把 skill 做成一个斜杠命令
塞进 `.claude/commands/`，然后检测模型有没有调用那个命令。而本机 `~/.claude/skills/`
里已经装着真的 attest ⇒ 模型直接加载真 skill，探针命令一次都没被调用 ⇒
实测率全是 0.00（含"help me write a test plan"这种明显的匹配）。那是评测环境被污染，
不是真结果。

`measure_triggers.py` 测的是真机制：skill 装在 skills 目录里，模型看到 name+description，
决定用不用它 ⇒ 表现为 `Skill` 工具调用里 skill 名匹配。

### 两个容易踩的坑

1. **评测仓库不能是空目录**。查询里提到的 `src/billing/`、`docs/refund-test-plan.md`
   在空目录里不存在 ⇒ 模型探一圈发现没东西可查就跳过 skill（实测：它在思考里提到了
   attest，但没加载）。所以评测器先造一个骨架仓库。
2. **`--max-turns 1` 会让测量偏保守**。模型习惯先探索代码、再决定加载哪个 skill，
   截在第一轮就看不到触发。给 3 轮。

### 读结果

- **精确率**（不该触发的有没有触发）比召回率更要紧：误触发会让 skill 到处插手。
- 漏触发时看输出里的 `other_skills`：模型改用了别的 skill ⇒ 是"我们被更强的候选挤掉了"，
  要改 description；没有 ⇒ 它压根没想到有这回事，description 得把那个主题写进去。
- **被当候选**（`considered`）：模型在思考里有没有提到我们。skill 列表本来就在上下文里，
  所以"没提到"不等于"没看见"——真正要问的是描述够不够显眼、能不能进候选集。

## 实测结果（2026-11-14）

三版 description，各跑 20 条查询（10 正 + 10 近邻反例），3 轮，真实装在 skills 目录里测。

| description | 精确率 | 召回率 | F1 | 命中的查询 |
| --- | --- | --- | --- | --- |
| v0（原始） | **1.0** | 0.4 | 0.571 | 1, 2, 3, 6 |
| v1（补回主题簇 + 问题形态） | **1.0** | 0.3 | 0.462 | 1, 2, 8 |
| **v2（补字面词 + 输出词汇）** | **1.0** | **0.5** | **0.667** | 1, 2, 3, 8, 10 |

**精确率三版都是 1.0**：10 条近邻反例一条都没误触发，包括"把 jest 换成 vitest"
（近邻）、"怎么搭一套端到端测试环境"（泛化测试问题）、"unit test 一般怎么写"
（泛化）、"把上个月的覆盖率报告导出来"（近邻）。这一项是最要紧的。

**召回率的损失结构**（v2）：10 条该触发的里，**6 条我们进了候选集**（模型思考时提到
我们），5 条真正加载了。也就是说：描述显眼度够（60%），**输在最后的选择上**——
输给的对手是泛化能力：`ecc:production-audit`、`analyze`、
`superpowers:systematic-debugging`（"数据在漂"被归成调试）。

### 三条要记住的解读

1. **这个数测的是竞争环境，不是描述的绝对质量。** 本机装着 60 多个 skill（含
   `ecc:*`、`analyze`、`superpowers:*` 这些泛化能力），我们要在它们中间赢。OSS 用户
   装上时 skill 集合不同，数**不可直接迁移**。它是发布前的参考，不是质量指标。
2. **别对着这个指标调 description。** v1 就是这么干出反效果的（0.4 → 0.3）：把描述改长
   之后，某些原本命中的查询掉了（新描述里那些词不再显眼）。20 条样本、每条跑 1 轮，
   ±1 条查询就是 ±0.1 召回率 —— 在这个样本量上调参是在拟合噪声。
3. **v2 为什么比 v1 好**：v1 只补了"主题簇"，v2 补了**字面词**与**输出词汇**。
   用户打的是"跑一下**交付就绪度**"，而 v1 的触发词写的是"测试就绪度" —— 字面不对
   就匹配不上。补上之后 query 3 回来了。输出词汇（已实测 / 静态信号 / 无信号 /
   本工具不判定）让模型能认出"这个工具产出的正是我要的"，query 10（生成测试骨架）
   也回来了。

## 实测结果（2026-11-23）：description 压到 191 字符后的同模型 A/B

SkillEvaluator 复评要求 description ≤ 200 字符且「Use when」出现在前 60 字符里
（有些 harness 只显示前 60 个字符）。改完之后**用同一套查询、同一个模型、同一天**做 A/B，
确认没有把触发面改坏：

| description | 精确率 | 召回率（10 条正例） | 被考虑过（considered） | 花了 |
| --- | --- | --- | --- | --- |
| 旧（211 字符，`Requirement test plan + delivery readiness: …`） | **1.0** | 0.2（2/10） | 4 | $3.09 |
| **新（191 字符，`Use when writing a test plan, …`）** | **1.0** | **0.4（4/10）** | 5 | $7.23（全 20 条） |
| 新 + 「两边对不上」 | **1.0** | 0.3（3/10） | 6 | $2.97 |

**结论**：

1. 压到 191 字符 + 「Use when」提前，**召回从 0.2 翻到 0.4**，精确率仍是 1.0
   ⇒ 这处改动是**改进**，不是拿评测指标换分。
2. 再加「两边对不上」（为 Tier 3 里那条跨存储漂移用例的字面词）**没有帮助**（0.3 比 0.4 少一条）
   ⇒ 按本文件下面那条规矩（±1 条查询就是 ±0.1 召回率，这个样本量上调参是在拟合噪声），
   **不加**，已撤回。
3. 绝对值比 2026-11-14 那版低（0.5），是**竞争环境变了**：本机现在装了 255 个 skill
   （当时 173 个），同一个 description 在更挤的候选集里赢面更小 —— 这与本文件开头第 1 条
   说的是同一件事：这个数不是描述的绝对质量。

**一条测量的坑**：这轮里有不少查询是 `--max-turns 3` 截断的（模型还在探仓库、没轮到加载
skill）⇒ 部分「没触发」是**测量窗口不够**，不是描述不匹配。要看真实触发率得给更多轮数。

### 复现

```bash
python3 evals/measure_triggers.py --max-turns 3            # 一次跑完（约 $5-8）
python3 evals/measure_triggers.py --from 1 --to 5          # 分块跑（后台任务活不过重启时分块用）
```

分块参数 `--from/--to` 是为了在长任务里保住进度：一次跑 20 条要十几分钟，中途断了
就全丢；分块跑每块五分钟，断了只丢一块。
