# 示例：一次真实的跨存储对账（来自一个具体项目）

这份文档把 SKILL.md 里"租户口径"与"跨存储字段级比对"的判据，用一个真实项目的
数据讲清楚。**具体项目名与租户名都做了脱敏** —— SKILL.md 的正文里不该出现
任何一家客户或内部项目的名字。

## 场景

模块 `agent-memory`（向量记忆）同时写两个存储：

- **权威库**（PostgreSQL）：行数据、租户、状态
- **派生库**（Milvus）：向量与文档内容

派生库是从权威库镜像出来的。**两边会漂**：写权威库成功、写向量库失败 ⇒ 权威库有行、
向量库没有对应的向量。

## 怎么判（租户口径）

测试用例常**刻意**造出失败态来验证容错路径：

| 租户 | 怎么来的 | 算不算漂移 |
| --- | --- | --- |
| `default` | 生产租户 | **fail** —— 阻塞交付 |
| `memtest-r5-skip` | 测试用例**直接 DB insert** 塞的配额占位（绕过写路径 ⇒ 天然无向量） | warn —— 夹具状态，不是缺陷 |
| `itest-r4-contract` | 测试用例**注入镜像失败**造出来的 | warn —— 同上 |

判定结论：生产租户一致 ✅；两个测试租户的"缺向量"是刻意的。

**这两行数据不能清** —— 清理脚本（`memory-r5-cleanup`）只清 `memtest-` 前缀，
显式保留 `default` / `r4-review` / `mock-tenant` / `eval-tenant`。
R4/R5 的验收报告指着它们：清了报告引用的交付物就毁了。

> 这就是"租户口径"这条判据的由来：把夹具状态算成阻塞项 = 假阳性；
> 不区分租户又把真漂移放过去 = 假绿。

## 字段级比对（比行数更隐蔽的缺陷）

"两边行数不一样"很容易发现。**同一个 id 在两个存储里的同一个字段值不一样**更隐蔽：
读到的和写下的不是同一份数据，而行数对得上。

做法：对账脚本把两边导成 CSV，按 id 键做逐字段比对：

```
权威库.csv:  id | content | created_at
向量库.csv:  id | content | created_at
```

- 只在一侧出现的行 ⇒ 那是缺向量/孤儿向量，对账脚本自己报，不算字段不一致
- 两侧都有但**同名字段值不同** ⇒ 字段级不一致
- **时间戳类字段**天然会不同（导出时刻不同）⇒ 排除
- **正文类字段**（`content`）不一致 ⇒ **报给人判断，不自动判 fail**
  —— 自动修会掩盖写路径缺陷，而自动判红又会误伤"导出顺序不同"这类无害差异

## 复用的对账脚本

这个项目的对账脚本在 `service/scripts/memory-data-reconcile.ts`，
`package.json` 里叫 `reconcile`。工具**驱动它**而不是另写一套：
领域里已有的对账脚本知道那些关键取舍（比如"正文不一致要人判断、不能自动修"）。

自动化跑的时候把它的报告输出目录指到临时目录（`REQ_PLAN_RECONCILE_OUT_DIR`），
别覆盖人工当天那份。

## 教训

1. **租户不是噪声**：测试租户的数据是刻意的，直接算阻塞项 = 假阳性。
2. **缺行与行不符是两种缺陷**：后者更隐蔽，要按 id 做字段级比对才看得见。
3. **别自动修**：对账脚本知道哪些差异要人判断，工具不该替它决定。
4. **复用领域实现**：对账、覆盖率闸门、基线对拍，都驱动项目自己的脚本。
