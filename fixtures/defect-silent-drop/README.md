# fixture：defect-silent-drop

适配器把缺 id / 缺正文的行**静默丢掉** —— 不报错、不留痕。

**期望判定**

| 判据 | 期望 |
| --- | --- |
| 退出码 | `1` |
| 计划对齐 | 出现「机器推导出、计划里没有：1 条」⇒ `drop` 类判定点在计划里漏了 |
| 高危缺口 | 出现「高危四类缺口：drop 1」⇒ `drop` 被算成高危四类之一 |
| 缺口清单 | 出现「计划里没有这条判定点」⇒ 缺口有具体落点，不是只报个数 |
| 误报为 0 | **不**出现「resource 1」「error-path 1」⇒ 这类行过滤不该被算成资源/异常缺口 |

**为什么有它**

`filter` 掉一行是**合法的业务行为**（缺 id 的行本就不该入库），
但**静默**丢掉是另一回事 —— 它是 `drop` 类高危判定点：需求里没说清丢哪几行、
丢了之后谁负责补，测试里也没有一条断言钉住"丢的是哪一行"。

这个 fixture 的计划**刻意漏掉第一道过滤**（缺 id 的行），
只有机器反向推导才能发现它 —— 这正是「计划格式从模块级维度升级到判定点粒度」
要解决的问题：人在计划里漏了一行，工具要能指出来，而不是给一句"覆盖到位"。

**怎么跑**

```bash
bash fixtures/run_fixtures.sh          # 全部 fixture
```

单独跑这一个：

```bash
cd fixtures/defect-silent-drop
python3 ../../scripts/readiness.py src --repo . --plan plan.md
```

**已知的环境依赖**

需要 `node`（22+，能直接跑 `.ts`）。
判定点推导需要 TypeScript 后端（仓库内或全局 `tsc`）；没有时推导等级降到 L2
（词法层），本 fixture 的 DP 集在 L2/L3 下相同 ⇒ 结论不变。
