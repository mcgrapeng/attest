# 需求级测试计划

接到一个需求时，产出一份**可核对的**测试工具集：每条行为契约有钉、每个关键流程
有测试落点、每份产出数据有一致性核对方式、已有能力先复用。

## 一条命令：交付就绪度判定

```bash
python3 "$SKILL_DIR/scripts/readiness.py" <模块路径> --repo <根> \
  [--plan <需求测试计划>] [--include-itest] [--test-tenant <名字或前缀>] \
  [--mutation-check] [--json]
```

`$SKILL_DIR` = 本 skill 所在目录（装在 `~/.agents/skills/attest` 时就是那个路径）。

回答的是：**这个模块的交付前提里，哪些已被实测证明、哪些还没被证明、哪些本工具判不了。**

它**不是**「能不能交付给客户」的裁决 —— 需求是否被正确理解、产品行为、性能、安全、
可用性、运维就绪都不在判据范围内，报告里有一节固定列出这些（见「输出契约」）。
交付决策仍归人。

每条判据要么有实测证据，要么明说「未实测（缺什么条件）」—— 不拿静态推断冒充实测：

| 判据 | 证据类别 | 怎么测 |
| --- | --- | --- |
| 测试全绿 | 实测 | 用**项目自己的** test 命令跑模块测试，列出失败用例（**只认断言失败**；setup 报错=环境没就绪 ⇒ 未实测） |
| 核心逻辑测试到位 | 实测 | **驱动仓库自己的覆盖率闸门**（没闸门才用 `--min-line-coverage` 显式指定；默认不阻塞） |
| 测试能发现缺陷 | 实测 | 把源码改坏（改比较运算符）再跑测试：测试红了=杀得死，测试还绿=**这套测试发现不了这类缺陷**。要 `--mutation-check`（复制工作区并多次跑测试，很贵，默认不跑 ⇒ 默认是「未实测」） |
| 表结构基本合规 | 实测 | 查 PG catalog：主键/唯一约束/租户列/RLS+FORCE/时间戳带时区（单租户、配置表、追加表有豁免） |
| 数据流一致（跨存储对账） | 实测 | **实跑**模块自己的对账脚本，解析漂移；**按租户口径**判；字段级比对并入这条 |
| 数据准确（基线对拍） | 实测 | **实跑**项目的基线对拍脚本，解析指标差异 |
| 钉有区分力 | 实测 | 在钉的位置把源码改坏、跑钉住的那个用例：红了=杀得死，还是绿=**这条钉发现不了这类缺陷**（要 `--plan` + `--discriminating`；不给计划 ⇒ 未实测。`auto` 模式只对判定点粒度（v2）的计划跑，旧格式（v1）的计划会被静默跳过 ⇒ 那种情况要显式 `--discriminating quick` 或 `full`） |
| 向量集合属性自洽 | 静态 | 同一集合在不同调用点的维度/度量/分区键是否一致；分区键不能是向量字段；写入的集合与检索的集合是不是同一个（集合侧与 PG 侧对称的那条） |
| 测试卫生 | 静态 | 读测试源码：固定等待（flaky 源）与不清理的写库测试（残留源）⇒ 报 |
| 导出的逻辑都有测试 | 静态 | 读测试源码找引用：导出的函数/类零引用 ⇒ 点名（TS 导出 / Python 公开 def·class / Rust `pub fn`） |
| 需求覆盖到位 | 静态 | 读计划与测试文件：每条不变式的钉 → 真实存在的用例（`--plan`） |
| 不过度抽象 | 静态 | 导出符号全仓几乎没有调用点（规则之三） |
| 没有重复造轮子 | 静态 | 全仓同名实现（跨域同名降为提醒） |
| 使用主流开源库 | 静态 | 模块真实依赖清单（排除路径别名与标准库） |
| 断言的期望值独立 | 静态 | 期望值取自被测对象自身的断言（恒真的同义反复单独点出）⇒ 提醒 |
| 计划与机器推导对齐 | 静态 | 从源码反推判定点，与计划里的判定点列**双向**对账：机器有计划没有、计划有机器没有、钉的路径根本不在这个模块里（`--plan`） |
| 应有判定点覆盖到位 | 静态 | 计划里每个高危判定点都有不变式认领**或**写明豁免理由，且落点（file::case）真实存在（`--plan`） |

**证据类别说的是"这条判据靠什么得出"**（跑出来的 vs 读源码读出来的）。
它同时决定了报告里它落在哪一节：**静态信号永远不能单独支撑「通过」**。
类别按**每次结果**标 —— 需要数据库的判据连不上库时会标成「未实测」而不是「实测」。

任何一项「不通过」⇒ 结论里算**阻塞项**，退出码 1。

**实测的前提**：用项目自己声明的 test 命令（有些项目用 tsx 这类 runner，
路径别名要它才解析）。裸 `node --test` 会让一堆测试假挂 —— 那测的是假象。

## 存储类模块：数据流自身要审出来

模块碰了 PG 之外的存储（向量库、对象存储、消息队列），交付判定要覆盖**数据本身**，
不只是"代码跑通了"。工具的做法是**驱动领域里已有的专家实现**，不另造一套：

- **数据流一致**：找出模块自己的对账脚本（脚本名在白名单里、且脚本文件提到该模块的
  表），**实跑**，解析漂移行。领域已有的对账脚本知道那些关键取舍（例：正文不一致要人
  判断、不能自动修 —— 自动修会掩盖写路径缺陷）。自动化跑的时候把脚本的报告输出目录
  指到临时目录（`REQ_PLAN_RECONCILE_OUT_DIR`），别覆盖人工当天那份。一致与漂移的租户
  都要列出来 —— 只列漂移的会让人以为生产租户也漂了。
  **漂移的识别方式可配**（`--drift-pattern`）：原来写死「中文『漂移』+ ❌」两个特征，
  英文输出的对账脚本一律假绿。现在默认认 `❌ / 漂移 / drift / mismatch`，租户列从
  表头认（不是写死第一列），测试租户前缀可配（`--test-tenant-prefix`）。
- **字段级跨存储比对**（并进「数据流一致」这条）：同一个 id 在 PG 和向量库里的
  **同一个字段**值对不上，是比"两边行数不一样"更隐蔽的缺陷（读到和写下的不是同一份
  数据）。仓库自己的对账脚本通常只比 id 集合与正文，但它往往把两边**导成 CSV** ——
  在导出上按 id 键做逐字段比对即可，不用另写一套向量库查询。只在一侧出现的行不算字段
  不一致（那是缺向量/孤儿向量，对账脚本自己报）。CSV 按声明的对照关系配对
  （`--csv-pair a.csv=b.csv`），不是两两配对；**时间戳类字段排除**，正文类字段单独
  归类并报「需人工判断」，**不自动判 fail**；找不到成对的 CSV ⇒ 报「无法比对」，
  不报「0 对无差异」。
- **数据准确**：实跑**这个模块的**基线对拍脚本（`eval:baseline:check` 之类），解析指标差异。
  跟对账车道同一个口径：脚本要么在模块自己的 workspace 里，要么脚本正文/命令提到该模块
  （表名或模块路径）。多包仓库里别处的基线脚本指标口径不是一回事，报出来的差异是别的域的
  ⇒ 不算这个模块的证据。
- **向量集合属性自洽**（与 PG 侧对称的那条）：PG 侧有五条自有规则，集合侧也得有。
  判的是**调用点之间是否自相矛盾**，不猜项目的命名规范：
  - 同一集合在不同调用点的维度/度量/分区键不一致 ⇒ 报（写入用 1536、检索用 768
    这种，工具看不出来就等于没测）；
  - 分区键指向一个向量字段 ⇒ 报（向量库不允许按向量字段分区）；
  - 写入的集合与检索的集合不是同一个 ⇒ 提醒（若本意是同一份数据，这就是
    "写入 A、检索 B"的缺陷）。

  **不判**集合命名规范，也**不判集合与线上真实租户是否一致** —— 前者要项目的约定，
  后者要连活的向量库并用项目自己的凭据（本工具不替项目保管向量库凭据）。要判线上
  一致性，得由项目出一个「集合 schema 快照」脚本，工具去跑它（同对账脚本那条路）。

**漂移怎么认（这条是对外契约，改了会影响所有用这个 skill 的项目）**：

- 报告是**表格形态**时，漂移**只从数据行**认。表头行（下一行是 `|---|---|` 分隔行）
  与分隔行本身都不是数据。
- 报告是**纯文本**（没有表格行）时，按行匹配，只排除**伪表头**（带 `|` 且像表头的那行）。
- **数据行不会因为含 `租户`/`tenant`/`一致性` 字样被丢掉** —— 那是把数据行当表头，
  真漂移会被静默吞掉（假绿）。例：`| default | 10 | 正文不一致 |` 是数据，不是表头。
- 散文里的「漂移」是说明文字，不算漂移行（表格形态下本来就不进候选；
  纯文本形态下仍然会被算 —— 纯文本没有表结构可认，这是那条路的固有上限）。
- 「N 个生产租户漂移」数的是**去重后的租户数**，不是命中行数。
- 识别方式可配：`--drift-pattern`（默认认 `❌`/`漂移`/`drift`/`mismatch`）、
  `--table-header-pattern`（默认认 `一致性`/`租户`/`tenant`/`---`，只用于兜底认表头）。

**已知边界**：文本抓取认不出"换了说法"的报告 —— 行级判据既没有 ❌ 也没有默认关键词时，
漂移会看不见（判成"无漂移"）。这是这条路的固有上限，不是配置问题。真要稳，
**对账脚本应当输出表格或 JSON**：表格里把行级判据放在固定的一列（例 `| 租户 | … | 判定 |`
且单元格里写 `✅ 一致` / `❌ 漂移`），JSON 则直接把漂移租户列出来。

**「跑不起来」和「不达标」必须分开**。脚本因为**没有产物**而失败（"先跑 eval 套件
再对拍"）是环境没准备好，不是数据回归 —— 判成「未实测」并说清缺什么；
只有真的解析出指标差异才报红。这条最容易出假阳性。

**按存储类型定判据**，别一律报红：

| 模块碰到的存储 | 判定 |
| --- | --- |
| 只有一个 PG | 未实测 —— 没有派生层可跨存储校对 |
| PG + **派生存储**（向量库 / 对象存储） | fail（除非有对账机制）—— 权威与派生会漂 |
| PG + **旁路存储**（Redis / 队列） | warn —— 确认它不是权威数据 |

**别对不懂的东西给结论**：识别不出源码文件 ⇒ 退出码 2 + 说清原因（不要输出一堆
关于"空"的 ✓）。Rust / Go 模块目前识别不出来 ⇒ 同样退出码 2 + 说清"当前只实现了
TS/JS/Python"。一个满屏 ✓ 但其实什么都没测的报告，比报错更糟。

**Python 工程**（pytest 系）也判：

- 覆盖率用 `pytest --cov=<包> --cov-report=json`（coverage.py 的合并是确定的 ⇒ 一次就够）。
- **仓库自己的闸门优先**：读 `pyproject.toml` 的 `[tool.coverage.report] fail_under`、
  `Makefile` 的覆盖率目标、`tox.ini` 的环境，闸门的退出码即结论 —— 门槛归仓库所有，
  不用通用阈值。
- 导出 = 模块级公开 `def`/`class`。**别把接口与生成码当逻辑**：`Protocol`/`ABC`/`Generic`
  是接口（对应 TS 的 `interface`/`type`）、`.pyi` 与 protobuf/grpc 生成码不是人写的、
  类体里没有任何 `def` 的纯数据类（DTO/响应模型）只是数据形状 —— 这三类都不算
  "待测导出"，否则噪声盖住真缺口。
- **测试文件三种位置都算**：模块目录内 colocated 的 `test_*.py`（Python 的惯例就是把
  测试放在包旁边）、仓库级 `test/` `tests/` `spec/` 下的 `test_*.py` / `*_test.py`。
  漏掉 colocated 那一种会把整类仓库的公开 def/class 全判成"零引用"。

覆盖率同理：单元测试车道和真后端 itest 车道是两条道。只跑单元车道时报
"service.ts 7%"会被误读成"那文件没人测" —— 实际它的覆盖来自 itest 车道。
默认报覆盖率时要把「另有 N 个 itest 用例未计入」说出来，`--include-itest` 才合并算。

## 覆盖率必须是确定的

**同样一条命令跑两次，覆盖率数字必须一样** —— 否则它不能用来判交付。

node 的 `--experimental-test-coverage` 在**用了 `mock.module()` 的项目**里，
跨 worker 合并覆盖率会竞态：实测同一个模块，同一条命令，覆盖率在
7.26% 与 59.45% 之间跳（文件级独立翻转，测试全绿、数字乱跳）。

**优先级：仓库自己的闸门 > 通用并集**。

- 仓库有覆盖率闸门（脚本名在白名单里、命令含 cov、提到该模块）⇒ **驱动它**，判定看它的
  退出码 —— **门槛归仓库所有**。通用阈值在这里是错的：有的仓库把行覆盖 49% 的
  文件明确列为合格，通用阈值（行 80）会把这些文件判红。
  仓库拆闸的原因也写进了它的 AGENTS.md：每闸只测自己那批、只在该批里加载，
  数字才可复现 —— **别拿通用阈值去覆盖仓库的口径**。
- 仓库**没有**闸门 ⇒ 判「未实测：仓库没有覆盖率闸门，缺少判据」，**默认不阻塞**。
  真要一个通用门槛，用 `--min-line-coverage` / `--min-branch-coverage` 显式指定
  （数字由你定，工具不替你猜）。
- 仓库没有闸门但仍要覆盖率数字 ⇒ 逐个测试文件单独跑（各自独立进程 ⇒ 没有合并 ⇒ 确定），
  再取覆盖**并集**（未覆盖行取交集）。并集回答的正是"这行代码有没有被任何
  测试执行过"。分支/函数覆盖率没有区间数据可并 ⇒ 取各次最大值（偏保守）。

**真后端（itest）车道默认不跑**，要 `--include-itest` 才跑：驱动仓库自己的 itest 脚本
（原样跑，它自带 `MEMORY_ITEST=1`、`--test-force-exit`、钉死清单），只在 runner 参数后、
文件参数前插覆盖率参数 ⇒ 一次跑出「用例全绿」+「真后端覆盖率」。两条车道分开报，
别混成一个数。默认不跑是因为它要连 PG + 向量库、慢，而且环境没就绪时会刷一片报错。

**真后端车道也要分「环境没就绪」与「用例真失败」**：换台机器（CI、同事电脑）
没有 Milvus/PG 时，车道会连不上 —— 那是环境问题，不是产品缺陷 ⇒ 判「未实测」，
不进阻塞项。判据看失败块的 `error:` 详情（用例名里没有报错文本）：
`ECONNREFUSED` / `InvalidPassword` / `UNAVAILABLE` / `connection refused` 等。
注意用例名可能带 `# SKIP set MEMORY_ITEST=1 with local Milvus+PG running`
—— 那句就是仓库自己写下的环境前提。

**显式清单优先于 glob**：仓库钉死文件清单是有意的（glob 会把在途文件一起吸
进来，红灯与产品无关）。

## 覆盖率高 ≠ 测试有劲

**覆盖率只说明代码被执行过，不说明断言会失败。** 一个"杀不死缺陷"的测试套件，
覆盖率再高也不说明问题 —— 它测的是"这行代码跑过"，不是"这行代码错了会不会被发现"。

所以另有一条实测判据「**测试能发现缺陷**」：把源码改坏，再跑该模块自己的测试。

- 只改**比较运算符**（`==` / `!=` / `===` / `!==` / `>=` / `<=`），不改常量、不改字符串、
  不改控制流 —— 那些变异容易变成"编译错误"或"改了无关的语义"，测出来的结论不可靠。
  字符串与注释里的运算符不碰。
- 测试红了 ⇒ 变异被**杀死** ⇒ 这套测试能发现这类缺陷；测试还绿 ⇒ **杀不死** ⇒
  测试套件有洞，报告里点名是哪个文件的哪一行。
- 跑在**仓库副本**里（依赖目录软链），**绝不改用户仓库**。
- **默认不跑**（`--mutation-check` 才跑）：它要复制工作区并多次跑测试，很贵。
  不跑时这条判据是「**未实测**」，不是"通过"。
- **不设分数线**：杀不杀得死多少算够，门槛归项目。工具只报事实与位置 ——
  `0 个杀死 ⇒ 阻塞`、`部分存活 ⇒ 待人工确认（列出位置）`、`全部杀死 ⇒ 通过`
  （并注明"样本有限 ⇒ 不等于这套测试够强"）。
- **环境没就绪 ≠ 杀死了**（同「跑不起来 ≠ 不达标」那条）：测试因为连不上中间件而红，
  或者 runner 的输出认不出用例名 ⇒ 那个变异点**判不了**（既不算杀死，也不算存活）。
  只看退出码的话，环境错误会被算成"杀死了" —— 一个专测"测试有没有劲"的工具
  自己假绿，比没有这条判据更糟。

## 判交付看生产租户

测试用例常**刻意**造出失败态：注入镜像失败、直接插库塞配额占位。这些不是
数据漂移，是夹具状态。**把它们算成阻塞项 = 假阳性**。

| 租户 | 漂移怎么算 |
| --- | --- |
| 生产租户 | **fail** —— 阻塞交付 |
| 测试租户（名字像 itest-/memtest-/mock-/eval-…，或 `--test-tenant` 声明的） | warn —— 信息，不是阻塞 |

实测（一个向量记忆模块）：生产租户 ✅ 一致；两个测试租户分别有 50 行和 4 行
没有向量 —— 前者是测试用例**直接 DB insert** 的配额占位，后者是**注入镜像失败**
造出来的 —— 两个都不是缺陷。按租户口径判之后，这条判据才准。
完整案例见 [examples/cross-store-reconciliation.md](examples/cross-store-reconciliation.md)。

## 「跑不起来」和「不达标」必须分开

脚本因为**没有产物**而失败（"先跑 eval 套件再对拍"）是环境没准备好，不是数据
回归 —— 判成 skipped 并说清缺什么；只有真的解析出指标差异才报红。

pytest 的 `ERROR`（fixture/环境没就绪，例：连不上 PG）与 `FAILED`（断言没过）
同理：**只有 FAILED 才是"测试没绿"**。这条最容易出假阳性。

## 输出契约：证据清单，不是裁决

报告按**证据类别**分节，不是一张平铺的 ✓/✗ 表：

| 节 | 里面是什么 |
| --- | --- |
| 已实测 | 真跑出来的（测试、覆盖率闸门、对账脚本、基线对拍） |
| 静态信号 | 源码扫描与词频分析得出的（测试卫生、不过度抽象、重复造轮子、依赖清单、oracle 独立性）—— **永远不能单独支撑「通过」** |
| 未实测 | 没测到、判不了的（○） |
| 本工具不判定 | 需求是否被正确理解 · 产品行为 · 性能 · 安全 · 可用性 · 运维就绪 |

结论是三档：**N 项阻塞 · M 项待人工确认 · K 项无信号**。

**为什么不是「能不能交付」**：工具掌握的是 14 条机械判据的实测状态，不是这个模块的
交付裁决 —— 中间那层推理（需求对不对、性能、运维）没有写在任何地方。输出证据清单，
决策留给有职责的人。

**退出码**：有阻塞项，或关键判据（测试是否绿）没测到 ⇒ 1；否则 0。
零测试的仓库在 CI 里必须拿到红灯 —— 那正是"没有测试就别说能交付"。

## 测试要自己收场

**测试往共享库里造的数据不清理 ⇒ 下一个测试看到的是别人的残留。**
（一个向量记忆模块的测试租户就是这个形状：50 行配额占位留在库里。）

判据：测试文件有写库动作，却没有清场动作（收场钩子里没有 delete/truncate/
drop）⇒ 报出来。**只在 `before` 钩子清理**只能保证"不跨轮累积"，跑完仍留
最后一轮 —— 那也是残留。

注意：有些用例是**故意**留着的（"本文件产出的 PG 行 + 向量是人工核对的交付物"）。
这类要报给人看，由人判断，不自动清。

## 等结果，不要固定等待

`sleep(1500)`、`asyncio.sleep(2)` 这类固定等待是 flaky 的来源（同样代码两次跑
出不同结论）。要等的是**结果**：等条件成立，别等时间。

## 其余三条（靠人读，不硬编成检查）

- **别测实现细节**：钉的是**行为/不变式**，不是某个组件、某个 DOM 结构。
  用户要的是"能生成上个月的报表"，不是"日期选择器是 Material UI"。
- **断言要具体**："报表看起来对"是让执行者猜。"报表包含这 12 条任务记录，
  不多不少"才是断言。断言要独立取期望值（从接口/库里读），别用被测对象自己的
  输出当期望值。
- **失败要能定位**：用例名要描述**行为**（"月度报表包含工作区的已完成任务"
  而不是 "reports test"）；失败信息要带上期望值与实际值。

## 核心原则

**钉得实 ≠ 理解得对。** 钉住只证明"这条不变式挂在一个真实存在的用例上"，不证明
"这条不变式就是需求的正确理解"。理解错了但错得自洽时，工具会全绿 —— 这是它判不了的
（它明说不判这一项）。所以计划里有一节**「人工确认」**：谁读过、什么时候、对不对。
没填 ⇒ `check` 提醒，`readiness` 的报告把"需求覆盖到位"降成提醒级并明说
「计划未经人工确认 ⇒ 需求是否被正确理解未获保证」。填了才算 ✓。

**没有钉的不变式等于没测。**

"我测了" 不可信，"这条不变式钉在 `service.ts:427` + `write-gate-regression.itest.ts`"
才可信。脚本能机械核对的就是这件事 —— 钉指向的文件在不在仓库里、矩阵引用的测试
文件在不在、车道是不是编的。

## 什么时候用

- 新功能开工前，先出测试计划再写代码
- 需求有跨模块/跨存储的影响面，不清楚哪些测试车道要覆盖
- 已有计划要核一遍：声称覆盖了，但钉指向的文件不存在

## 跑法

```bash
# 1. 生成计划骨架（扫目标模块的已有 helper + 项目自己的测试车道）
python3 "$SKILL_DIR/scripts/req_plan.py new <feature> \
  --repo <项目根> --module <子路径> [--module <子路径>...]

# 2. 填完不变式与矩阵后，核对计划 vs 代码实况
python3 "$SKILL_DIR/scripts/req_plan.py check <计划文件> --repo <项目根>

# 3.（可选）把模块级维度表升级成判定点粒度，再分批填归属
python3 "$SKILL_DIR/scripts/req_plan.py upgrade <计划文件> --repo <项目根> \
  --module <子路径>
python3 "$SKILL_DIR/scripts/req_plan.py assign <计划文件> --repo <项目根> \
  [--limit 30]
```

计划落到 `docs/<feature>-test-plan.md`（入库、可评审）。`check` 有错误时退出码 1。

**`new` 默认不覆盖**：同名计划已存在时直接报错退出（退出码 1），文件原样保留。
要覆盖加 `--force`；想保留就换 `--out <别的路径>`。仓库没有 `docs/` 目录时会
自动建一个。

**`check` 强制两节**：不变式清单、覆盖矩阵（缺任一 ⇒ 报红）。复用表**有才查**
（不写不报错；写了"复用 XXX"却指不到真实文件 ⇒ 报红）。测试车道**会校验但只给提醒**
（不报红、不影响退出码）。

**跨存储时才校验**两节：数据一致性、约束（不引入中间件）。**触发条件是"有没有写
这两节"**，不是"表里有没有数据行" —— 写成散文、不写表格，都照样校验。写了这节
却没数据行 ⇒ 报红（没有跨存储就删掉整节）。

`new` 也按这个口径生成：模块只碰**一种**存储时**不生成**这两节（省得新计划一出生
就带着两条红），碰**两种以上**才生成。所以单存储模块的计划里找不到这两节是正常的。

一致性节按**表形状**也认（多列且含"权威源 / 镜像 / 派生 / 一致性怎么验"这类列），
所以标题叫 `## 跨存储核对` 也认得出来。

缺权威源、缺镜像说明、缺一致性落点、同一数据两行、没给替代方案、对账路径没落点、
拿中间件/分布式事务当解法 —— 全都报红。**中间件检查无条件跑**：不写一致性节
也拦不住"用消息队列保证一致"这种写法。否定语境（"本项目不引入消息队列"）不算。

**每张表按自己的表头定归属**，标题只在表头不认识时兜底。所以一个标题里混两节
不会吞表（但会提醒拆开）。表头用词随意（`| 场景 | 测试文件 | 车道 |` 认得）。

计划路径先按**当前目录**解析，找不到再按 `--repo` 根解析；两处都没有才报错
（退出码 1，`读不了计划文件`）。**表格每行都要以 `|` 开头**（GFM 允许省略，
但这里的解析器要求有）。

## 工作流

### 1. 影响面 + 复用侦察 + 存储清单（跑 `new`）

`new` 会扫出三样东西，先看它们再动手写代码：

- **本模块碰到的存储**：PG 表 / 向量集合 / 对象存储 / KV，带文件:行证据。
  **碰了 2 个以上存储 ⇒ 必须有「数据一致性」一节**（`check` 会强制）。
- **已有能力**：目标模块里扫描得到的**符号**（TS 的
  `export function/const/class/interface/type/enum`、`export {…}`（含
  `export { x } from './y'`）、解构导出、具名 `export default function foo()`；
  Python 的 `def` / `class`；Rust 的 `pub fn/struct/enum/trait/type/const/static`）。
  **写新代码前先在这份清单里找** —— 能调就别抄。这直接对应"防止重复造轮子"。
  扫不到 `export * from` / `export * as ns from` / 匿名 `export default`；
  嵌套解构（`export const { a: { b } } = obj`）整条跳过（同语句里的平级兄弟
  也会一起漏）；测试文件（`*.test.*` / `*.spec.*` / `*.itest.*`）里的符号不收。
  清单里可能混着**未 export** 的符号（普通 `const`、私有 `def`）——
  复用前先确认它是导出的。每模块最多列 40 个。
- **测试车道**：项目自己 `package.json` 里名字像测试的脚本。**车道只读 package.json**
  —— Python / Rust / Go 项目扫不到，会输出"没扫到测试车道脚本"，此时车道得自己填
  （`check` 对不存在的车道只给提醒，不报红、不影响退出码）。
  车道清单从项目读，不硬编码 —— 别自己编一个项目里没有的车道。

### 2. 写不变式清单

每行一条行为契约，格式 `| # | 不变式 | 钉在哪 |`。

**钉写 `测试文件::用例名`** —— 工具会核对该用例**真的存在于那个文件里**。
只写文件（`src/x.test.ts`）会提醒"没指到具体用例"：同一文件里测了别的用例
也算出过。

用例名支持 `describe` 嵌套（写全名 `外层 > 内层` 或只写内层名都行）、
`it.each` / `it.skip` / `it.only` 修饰符、Python `def test_…`、Go `func Test…`。

- 不变式 = **这需求必须永远成立的性质**，不是"功能描述"。"召回超时会降级为空"
  是性质；"实现召回功能" 不是。
- **钉在第三列**（不是最后一列 —— 多一列"备注"时钉仍在第三列）。
- 钉的两级强度：`文件::用例名`（工具核对那个用例**真的存在**）>
  `文件` 或 `文件:行`（都只到文件/行，一律提醒）。行号不额外校验。
- 钉写成 `path/to/file.ts:123`：**路径相对仓库根**；扩展名限
  ts/tsx/js/jsx/mjs/cjs/py/rs/go/java/rb/sh（指向 `.md`/`.yaml`/`.sql`/`.vue`
  会被当成"没有钉"）。**行号只是给人看的，脚本不校验它存在** —— 文件在就行。
  目录当钉一般会被扩展名白名单挡掉（报"没有钉"）；若目录名恰好以白名单扩展名
  结尾（如 `foo.ts/`），存在性检查会放过它。
- 不变式行可以三列（`# | 不变式 | 钉在哪`，钉在**第三列**），也可以两列
  （`不变式 | 钉在哪`，钉在**第二列**）。两列行若第二列不是钉路径 ⇒ 报"没有钉"。
- **编号**可以是字母开头（`I1` / `INV-2` / `inv-2`），也可以是纯数字或 `#3`；
  实在认不出会标成"第 N 行"，照样检查，不会静默漏掉。
- 没钉的不变式是未完成的。

### 3. 写覆盖矩阵

每行一个**关键流程**，列出测试落点。

关键流程 = 代码流程的每一个关键细节。只测主干的矩阵不算覆盖 —— 边界、错误路径、
并发、重试、降级、跨租户隔离，各占一行。

- 落点写在**第 2 列**，每行都要有。**落点要是测试文件**（`*.test.*` / `*.spec.*` /
  `*.itest.*`）；指向源文件 ⇒ 提醒（测试命名不合常规时会这样）。
- **描述列里提到的文件名不算落点** —— 落点列空着就是没测。
- 车道列填项目里的车道（`service#test:e2e` 或裸名）。中文描述（"单测"）跳过不查。

### 4. 核心逻辑细节（每个维度都要答）

"测出核心逻辑的细节"落到这张表上。

**哪些维度适用由代码特征推导**，不是固定清单 —— 固定清单会逼着人给无关的维度填
「不适用」，噪声盖住真缺口：

| 维度 | 触发条件（目标模块里出现） |
| --- | --- |
| 边界 | 长度/上下界比较、clamp、MAX_ 常量 |
| 错误路径 | throw / reject / catch / 错误类型 |
| 并发 | Promise.all / 全局状态 / 定时器 / 循环内 await |
| 重试 | retry / backoff / attempts / maxRetries |
| 幂等 | 去重 / 唯一约束 / onConflict / 指纹 |
| 降级/超时 | catch / timeout / AbortSignal / 降级返回 |
| 跨租户隔离 | tenant / orgId / withTenant / RLS |
| 权限 | authorize / permission / grant / role / accessLevel |
| 资源上限 | quota / rateLimit / budget / maxActive |
| 数据对账 | 目标模块同时碰 ≥2 个存储 |

`new` 生成的表里每行都带**触发证据**（哪个文件哪一行触发的），可以核对。
不适用这个需求的维度**根本不会出现**。

计划里可以补：`本需求额外涉及：资源上限、审计留痕`（这些维度也要答）。

### 4b. 判定点归属（v2 计划：升级后的那张表）

`upgrade` 把上面这张模块级维度表换成**判定点粒度**的表，一行一个代码里真正要选的
分支/边界/错误路径：

```bash
python3 "$SKILL_DIR/scripts/req_plan.py upgrade <计划文件> --repo <项目根> \
  [--module <子路径>...]
```

升级后表是六列：`| 维度 | DP ID | 判定点 | 归属的不变式 | 落点（文件::用例名） | 豁免理由 |`。
前两列机器填好（DP ID 与判定点），**后三列要人来判断**：这条判定点归属哪条不变式、
钉到哪个用例，或者写明为什么豁免。

**两条判据口径不一样，别混**

| 判据 | 强制范围 | 一个模块的量级 |
| --- | --- | --- |
| `readiness.py` 的「应有判定点覆盖到位」 | 只有高危四类（错误路径 / 资源上限 / 状态 / 丢弃，即 error-path、resource、state、drop）报红；常规判定点（分支、边界、并发）只计数 | 高危通常一百多条 |
| `req_plan.py check` | **每一条**判定点都要有落点或豁免理由，常规判定点也报红 | 全模块多少条就是多少行 |

所以顺序是：先把高危那批填完，`readiness` 那条判据就绿了；`check` 想全绿，还得把常规那批也逐条填上 —— 那是另一个量级的工时，要不要做是项目自己的取舍。

**三列各填什么**

| 列 | 填什么 |
| --- | --- |
| 归属的不变式 | 不变式清单里真实存在的编号（`I1`、`I2`…）。认领一条就必须给落点 |
| 落点（文件::用例名） | 钉到**真实存在**的用例：`service/src/agent-memory/lifecycle.itest.ts::某条用例`。只写文件会被提醒 |
| 豁免理由 | 认领不了时的出路：写清楚这个判定点为什么不用测。「不适用」三个字会被提醒 |

**用 `assign` 分批填，别手改表格**

上千行 markdown 表格手改既慢又容易错。`assign` 把填表变成一个可分批、可校验、
可增量提交的循环：

```bash
# 1. 拉待填清单（JSONL，一行一个判定点；高危在前）
python3 "$SKILL_DIR/scripts/req_plan.py assign <计划文件> --repo <项目根> \
  [--kinds drop,error-path,resource,state] [--offset 0] [--limit 30]

# 2. 回答写进 JSONL，一行一个：
#    {"dp_id":"…（原样抄回来）","invariant":"I3","pin":"path/to/x.itest.ts::用例名"}
#    或 {"dp_id":"…","waiver":"为什么这个判定点不用测"}

# 3. 写回：校验不过的不写，报出原因
python3 "$SKILL_DIR/scripts/req_plan.py assign <计划文件> --repo <项目根> \
  --apply answers.jsonl

# 4. 看缺口还剩几条
python3 "$SKILL_DIR/scripts/req_plan.py check <计划文件> --repo <项目根>
```

清单第一行是元数据：计划里全部不变式的编号与描述（认领时要用）、
待填总数、高危类型、答案格式。之后每行给 DP ID、类型、维度、源码那一句、
以及**候选测试文件**（同目录下源码里提到这个符号的测试文件）—— 用例名从候选
文件里读，别编。

`--apply` 会挡住四类错：归属的不变式不在清单里、豁免理由太笼统
（只有「不适用」这种）、落点文件不存在、落点用例在文件里不存在（报错时会把
该文件真实存在的用例名列出来）。被挡下的不写盘，其余照写。

填完跑 `check`：高危缺口会一条一条往下掉，没填的会继续报红。
**别为了让 `check` 过而改钉** —— 钉该指哪就指哪。

每个维度**要么有测试落点，要么写「不适用」+理由**。默默跳过 = 没测到
（`check` 会提醒哪些维度没考虑到）。

### 5. 新建能力（先论证不能复用）

新写的抽象/工具列这里，三列：能力 / 为什么不复用现成的 / 调用点。

- **符号全仓已存在** ⇒ 报红：直接复用，别再造一个。
- **调用点 ≤1** ⇒ 提醒：规则之三 —— 抽象要等第三个用例才抽，一个调用点先内联。
- 没写清楚为什么不能复用 ⇒ 提醒。

这是"不过度设计"和"不重复造轮子"的兜底。

### 6. 数据一致性（跨存储才写）

**先看计划里的「本模块碰到的存储」** —— 那是工具扫出来的，带文件:行证据。
碰了 **2 个以上存储**（PG / 向量 / 对象存储 / KV）⇒ **必须写这一节**，否则报红：
两个存储的数据会漂，而漂了没人发现。

表格式：`| 数据 | 权威源 | 镜像/派生 | 一致性怎么验（钉） |`。

- **权威源要单一。** 一份数据只有一个权威，其余都是派生。同一份数据列两行 ⇒ 报红
  （大小写/空格差异也算同一份）。
- 权威源、镜像/派生（没有就写"无"）都不能空。
- 第四列必须是**具体测试文件** —— "一致性怎么验"不是断言，是测试落点。
- **没有跨存储就删掉整节**（留一张空表会被判红）。

校对要覆盖三件事（对账/修复路径必须被测到）：掉的数据能补、重复的不产生、
跨租户的不误删。项目里已有对账机制就复用它，别另写一套
（一个真实案例见 [examples/cross-store-reconciliation.md](examples/cross-store-reconciliation.md)）。

### 7. 约束：不引入中间件

跨存储一致性的解法在本项目里长什么样（**不引入额外的协调组件**）。

已知的通用形状是 **单权威 + 镜像 + 对账**：

```
写 ──▶ 权威库（PG）────镜像────▶ 派生库（向量库）
              │                      │
              └────── 对账修复 ◀──────┘
```

不引入中间件也能拿到一致性，代价是要写对账与修复路径 —— 那部分**必须被测到**
（掉的数据能补、重复的不产生、跨租户的不误删）。

所以这一节要写两样：

1. 替代方案正文（谁是权威、派生出哪、怎么对账修复）
2. 一行「对账/修复路径的测试落点：src/x.test.ts」

写「用某个消息队列保证最终一致」而不给替代方案 ⇒ **报红**：本项目不引入中间件。
（注意别在计划正文里把这些组件名当成"我们要避开的"写出来 —— 会被当成
"用了中间件"；要表达"不引入"，写替代方案本身就够了。）

### 8. 生成测试工具包（`scaffold`）

```bash
python3 "$SKILL_DIR/scripts/req_plan.py scaffold \
  <计划文件> --repo <项目根> [--out-dir <生成根>]
```

工具会**先认出这个仓库的测试约定**（框架 / 断言风格 / 单元测试位置 / e2e 目录 /
夹具层 / 已有夹具清单），再按约定生成：

- 落点文件**不存在** ⇒ 生成骨架：文件头（钉了哪几条不变量）+ `describe`/`it`
  结构（用例名直接来自计划）+ 断言处留 TODO。
- 落点文件**已存在** ⇒ **不碰它**，只列出「这个文件要加哪几个用例」。

生成的骨架带 TODO —— 断言必须人来填（工具不知道期望值）。

### 9. 跑 `check`

```bash
python3 "$SKILL_DIR/scripts/req_plan.py check docs/<feature>-test-plan.md --repo <根>
```

报红类（这些退出码 1）：

| 报红 | 含义 |
| --- | --- |
| 钉指向的文件不存在 | 文件改名了，或这条不变式是编的 |
| 钉的用例在文件里不存在 | 钉错了用例名，或测的是别的用例 |
| 落点的用例在文件里不存在 | 矩阵写错了用例名 |
| 不变式没有钉 | 这条没测（含漏了钉列：两列行的第二列不是钉路径） |
| 矩阵引用了不存在的文件 | 测试还没写，或路径写错 |
| 矩阵这一行没有测试落点 | 流程写了但落点列空着 |
| 没找到不变式表 / 覆盖矩阵 | 少了一节，结构不完整 |
| 复用表引用了不存在的文件 | 声称复用的东西没有 |
| 数据一致性缺权威源 / 缺镜像 / 缺落点 / 同一数据两行 / 数据名为空 | 跨存储的一致性没法核 |
| 目标模块同时碰了 2 个以上存储，却没有一致性校对 | 两个存储的数据会漂 |
| 一致性落点指向的文件不存在 | 对账/一致性测试还没写 |
| 约束缺替代方案 / 缺对账落点 / 对账落点不存在 | 本项目不引入中间件 |
| 拿中间件/分布式事务当解法 | 改成「单权威 + 镜像 + 对账」 |
| 核心逻辑细节某个维度没有落点 | 这个维度没测到 |
| 新建能力的符号全仓已存在 | 重复造轮子，直接复用 |

提醒（不阻塞退出码，但必须处理）：车道不在项目里（编的车道）、落点不是测试文件
（测试命名不合常规）、一个标题里混了两节、没考虑到的核心逻辑维度、
新建能力没论证为什么不复用、调用点 ≤1（规则之三）、
**钉只到文件没指到用例**、**有没用例没有对应的不变式**（测试多余 or 漏了不变式）—— 范围是不变式钉过的文件 ∪ 矩阵落点文件。

复用表**只有含「复用 / 已有 / reuse / existing」字样的行**才会被校验。

**红的必须清掉才算完。** 不要改计划里的钉来骗过检查 —— 钉该指哪就指哪。

## 与 `ai-testing-system` 的关系

- `ai-testing-system` 管**项目级**：成熟度清单、工具矩阵、门禁分层、审计。
- 本 skill 管**需求级**：一个需求的测试工具集长什么样、每条契约钉在哪。

项目先跑 `testkit-audit` 看缺哪些车道，需求再跑本 skill 规划这一条需求的落点。

`check` 还会检查计划钉到的测试文件本身：

| 性 | 检查 | 级别 |
| --- | --- | --- |
| 严谨 | 测试文件里没有断言（覆盖率剧场） | 报红 |
| 逻辑 | 文件头没声明钉了哪些不变量 | 提醒 |
| 复用 | 测试里的助手与仓库已有导出重名 | 提醒 |
| 扩展 | 同一文件里多个用例结构雷同（该参数化） | 提醒 |

## 安全须知（`readiness.py` 会做什么）

这个工具的定位是"实测"，所以它**会执行目标仓库自己定义的脚本**。这不是副作用，
是它的本职 —— 但你得知道边界在哪：

- **默认就是执行**。不跑测试的交付判定没有意义，所以没有"必须显式开关才跑"这一层
  （brief 里要求过，改了：每次调用多打一个开关，收益不大）。它的安全边界是下面这三件套：
  **脚本白名单 + 执行前的审计行 + `--dry-run` 可预览**。
- **脚本选取分两种规则**（按生态不同，Python 那条更松）：
  - **JS 仓（`package.json`）**：**显式白名单** —— `coverage` / `test:coverage` / `cov` /
    `check:coverage`、`itest` / `test:integration`、`reconcile` / `data:reconcile`、
    `baseline:check` / `eval:baseline:check` 这些名字（精确名或冒号分段前缀）。
    `reconcile:reset`、`coverage:whatever` 这种名字里带关键词的**不会**被自动执行。
  - **Python 仓（Makefile / tox.ini）**：按**目标名里的关键词**认（`cov` / `reconcile` /
    `integration` / `itest`），且必须**成词** —— `coverage`、`test-coverage`、`py-cov`
    认，`recover`、`cover` 不认（子串匹配会把 `recover` 当成覆盖率闸门跑起来）。
    覆盖率闸门额外接受"模块目录或其上层"的 Makefile（所以全仓一个 `make coverage`
    仍然算数），对账与真后端两条车道还要求配方或命令提到本模块。
  - 不放心就用 `--dry-run` 看清楚到底会跑哪些目标。
- **执行前可以先看**：`--dry-run` 只列出将要执行的脚本与确切命令，然后退出。
  正常模式也会在报告头部回显一行「将执行的仓库脚本」，**包含仓库自己的 test 命令**
  （那是工具跑得最多的一层，逐个测试文件跑）。`--json` 时这行走 stderr，stdout 保持纯 JSON。
- **子进程只拿到白名单环境变量**（PATH、HOME、LANG、TZ、TMPDIR、SHELL、CI、
  `LC_*`、`NODE_*`、`PYTHON*`、POSTGRES_URL 等）。
  你 shell 里的**云厂商密钥**（`AWS_*` / `GCP_*` / `AZURE_*`）与**仓库凭据**
  （`NPM_TOKEN`、`NODE_AUTH_TOKEN`、`PIP_INDEX_URL` 里的密码、
  `UV_INDEX_SECRET_PASSWORD`）都**不会**传下去 ——
  `NPM_*`/`PNPM_*`/`YARN_*`/`PIP_*`/`UV_*` 这些前缀根本不在白名单里，
  `NODE_AUTH_TOKEN` 另外在拒绝名单上。仓库的 test 命令要 npm/pip 配置就用配置文件
  （`.npmrc` / `pip.conf`），别放环境变量。
- **PG 连接串不进命令行参数**：解析成 `PGHOST` / `PGPASSWORD` 等环境变量传给 `psql`，
  不出现在进程表里。注意 `POSTGRES_URL` 本身会透传给仓库自己的脚本（仓库的集成车道
  要连库）。真正能用的开关只有两个：把 `POSTGRES_URL` / `DATABASE_URL` 从环境里
  unset 掉、改用 `--database-url` 传（它不读环境变量，所以不会进子进程环境）；
  或者设 `PGHOST` / `PGUSER` / `PGDATABASE`，口令让 `psql` 从 `.pgpass` 读 ——
  只上 `.pgpass` 不够，schema 判定只读 `PG*` 变量，没有它们就判「未实测」。
- **只读为主**：`readiness.py` 不改用户仓库的任何文件。`req_plan.py scaffold` 会写测试
  文件，但写入范围被限制在 `--out-dir` 与仓库根之内；钉里带 `..` 或绝对路径 ⇒ 拒绝并
  报红，不写盘。
- **钉只能指向仓库内的文件**：越界的钉不读也不写（计划里的路径不能用来探测仓库外的
  文件）。

## 反向验证：证明这套判据抓得住东西

一个只输出绿色的判定工具，用户只能相信它的绿。`--self-check` 让工具**证明自己能失败**：

```bash
python3 "$SKILL_DIR/scripts/readiness.py" <模块路径> --repo <根> --self-check
```

它把仓库复制到临时副本，往副本里注入一个**已知缺陷**，再跑一遍判据，看它是否翻红：

| 注入 | 期望翻红的判据 |
| --- | --- |
| `drop-test` —— 清空一个引用了模块导出的测试文件 | 导出的逻辑都有测试（pass → fail） |
| `inject-sleep` —— 往测试里插一个固定等待 | 测试卫生（pass → warn） |

结论三种：**反向验证通过** / **反向验证未通过**（注入前就不绿，或注了也没翻红）
/ **没有可注入的故障目标**（模块没有测试文件 —— 那是"没法证明"，不是"证明没问题"）。
后两种退出码 1 —— 这是**工具自检**的结果，与模块本身的判定无关。

副本**默认不带 `node_modules`**，所以大部分仓库在副本里跑不动测试：这时翻红的是静态判据，
报告会明说「副本里跑不动测试」。要连实测项一起证明，加 `--self-check-deps`：

```bash
python3 "$SKILL_DIR/scripts/readiness.py" <模块路径> --repo <根> \
  --self-check --self-check-deps
```

它把 `node_modules` / `.venv` **软链**进副本（不复制体积）⇒ 副本里能真跑测试 ⇒
反向验证能覆盖**实测类**判据（测试是否绿、覆盖率），不只是静态判据。

## 常用命令

```bash
# 1. 生成需求测试计划骨架
python3 "$SKILL_DIR/scripts/req_plan.py new <feature> \
  --repo <根> --module <子路径>

# 2. 从计划生成测试工具包骨架（按仓库约定）
python3 "$SKILL_DIR/scripts/req_plan.py scaffold \
  <计划文件> --repo <根> [--out-dir <生成根>]

# 3. 核对计划 vs 代码实况
python3 "$SKILL_DIR/scripts/req_plan.py check <计划文件> --repo <根>

# 4. 模块交付就绪度判定（一条命令，实测）
python3 "$SKILL_DIR/scripts/readiness.py <模块路径> --repo <根> \
  [--plan <计划文件>] [--include-itest] [--test-tenant <名字或前缀>] [--json]

# 5. 先看会执行哪些仓库脚本（不执行）
python3 "$SKILL_DIR/scripts/readiness.py <模块路径> --repo <根> --dry-run
```

`readiness.py` 的常用参数：

| 参数 | 作用 |
| --- | --- |
| `--plan <文件>` | 把需求测试计划一起核（需求覆盖到位那条） |
| `--json` | 机器可读输出（checks + conclusion 段） |
| `--dry-run` | 只列将要执行的仓库脚本，不执行 |
| `--self-check` | 反向验证：往**副本**里注入一个已知缺陷，证明判据会翻红（不改你的仓库） |
| `--include-itest` | 把真后端（itest）车道并进来（要连 PG + 向量库，慢） |
| `--test-tenant <名/前缀>` | 声明测试租户（可重复）—— 测试租户的漂移是夹具状态，不阻塞 |
| `--test-dir <目录>` | 额外指定测试目录（默认找仓库级 `test/` `tests/` `spec/` 与模块内 colocated） |
| `--min-line-coverage` / `--min-branch-coverage` | 显式指定通用阈值（默认不阻塞，仓库自己的闸门优先） |
| `--drift-pattern` / `--table-header-pattern` | 对账输出的漂移/表头识别方式（对账脚本输出英文时用） |
| `--csv-pair a.csv=b.csv` | 声明 CSV 的对照关系（默认按共同列最多的互为最佳配对） |
| `--tenant-col <列名>` | CSV 里租户列的名字（默认按 `tenant_id`/`tenant` 认） |

## 常见错法

- **不变式写成功能描述** —— "支持导入" 不变；"导入的记录必须带 source 字段且缺失即拒收" 才变。
- **只测主干** —— 边界/错误路径/并发/降级/隔离各占一行，不是"一条流程走通"。
- **钉写成散文** —— `service.ts:427` 能 grep 到；"在 service 里" 核不了。
- **自己造车道** —— 车道从项目 `package.json` 读，编出来的跑不了。
- **矩阵引用还没写的测试文件** —— `check` 会报红；先写测试再填矩阵。
- **把判据当裁决** —— 报告给的是"哪些前提已被证明、哪些没有、哪些本工具判不了"；
  "能不能交付"是人的判断。别拿退出码当"质量已达标"的证明。
