# 判据的口径

每条判据到底怎么测、测不出来时怎么算、报告里怎么分层。入口那张表是速查，这里是不速查时的那份。

## 存储类模块：数据流自身要审出来

模块碰了 PG 之外的存储（向量库、对象存储、消息队列），交付判定要覆盖**数据本身**，
不只是"代码跑通了"。工具的做法是**驱动领域里已有的专家实现**，不另造一套：

- **数据流一致**：找出模块自己的对账脚本（脚本名在白名单里、且脚本文件提到该模块的
  表），**实跑**，解析漂移行。领域已有的对账脚本知道那些关键取舍（例：正文不一致要人
  判断、不能自动修 —— 自动修会掩盖写路径缺陷）。自动化跑的时候把脚本的报告输出目录
  指到临时目录（`REQ_PLAN_RECONCILE_OUT_DIR`），别覆盖人工当天那份。一致与漂移的租户
  都要列出来 —— 只列漂移的会让人以为生产租户也漂了。
  **漂移的识别方式可配**（`--drift-pattern`）：原来写死「中文『漂移』+ ❌」两个特征，
  英文输出的对账脚本一律假绿。现在默认认 `❌ / 漂移 / drift / mismatch`，租户列从
  表头认（不是写死第一列），测试租户前缀可配（`--test-tenant-prefix`）。
- **字段级跨存储比对**（并进「数据流一致」这条）：同一个 id 在 PG 和向量库里的
  **同一个字段**值对不上，是比"两边行数不一样"更隐蔽的缺陷（读到和写下的不是同一份
  数据）。仓库自己的对账脚本通常只比 id 集合与正文，但它往往把两边**导成 CSV** ——
  在导出上按 id 键做逐字段比对即可，不用另写一套向量库查询。只在一侧出现的行不算字段
  不一致（那是缺向量/孤儿向量，对账脚本自己报）。CSV 按声明的对照关系配对
  （`--csv-pair a.csv=b.csv`），不是两两配对；**时间戳类字段排除**，正文类字段单独
  归类并报「需人工判断」，**不自动判 fail**；找不到成对的 CSV ⇒ 报「无法比对」，
  不报「0 对无差异」。
- **数据准确**：实跑**这个模块的**基线对拍脚本（`eval:baseline:check` 之类），解析指标差异。
  跟对账车道同一个口径：脚本要么在模块自己的 workspace 里，要么脚本正文/命令提到该模块
  （表名或模块路径）。多包仓库里别处的基线脚本指标口径不是一回事，报出来的差异是别的域的
  ⇒ 不算这个模块的证据。
- **向量集合属性自洽**（与 PG 侧对称的那条）：PG 侧有五条自有规则，集合侧也得有。
  判的是**调用点之间是否自相矛盾**，不猜项目的命名规范：
  - 同一集合在不同调用点的维度/度量/分区键不一致 ⇒ 报（写入用 1536、检索用 768
    这种，工具看不出来就等于没测）；
  - 分区键指向一个向量字段 ⇒ 报（向量库不允许按向量字段分区）；
  - 写入的集合与检索的集合不是同一个 ⇒ 提醒（若本意是同一份数据，这就是
    "写入 A、检索 B"的缺陷）。

  **不判**集合命名规范，也**不判集合与线上真实租户是否一致** —— 前者要项目的约定，
  后者要连活的向量库并用项目自己的凭据（本工具不替项目保管向量库凭据）。要判线上
  一致性，得由项目出一个「集合 schema 快照」脚本，工具去跑它（同对账脚本那条路）。

**漂移怎么认（这条是对外契约，改了会影响所有用这个 skill 的项目）**：

- 报告是**表格形态**时，漂移**只从数据行**认。表头行（下一行是 `|---|---|` 分隔行）
  与分隔行本身都不是数据。
- 报告是**纯文本**（没有表格行）时，按行匹配，只排除**伪表头**（带 `|` 且像表头的那行）。
- **数据行不会因为含 `租户`/`tenant`/`一致性` 字样被丢掉** —— 那是把数据行当表头，
  真漂移会被静默吞掉（假绿）。例：`| default | 10 | 正文不一致 |` 是数据，不是表头。
- 散文里的「漂移」是说明文字，不算漂移行（表格形态下本来就不进候选；
  纯文本形态下仍然会被算 —— 纯文本没有表结构可认，这是那条路的固有上限）。
- 「N 个生产租户漂移」数的是**去重后的租户数**，不是命中行数。
- 识别方式可配：`--drift-pattern`（默认认 `❌`/`漂移`/`drift`/`mismatch`）、
  `--table-header-pattern`（默认认 `一致性`/`租户`/`tenant`/`---`，只用于兜底认表头）。

**已知边界**：文本抓取认不出"换了说法"的报告 —— 行级判据既没有 ❌ 也没有默认关键词时，
漂移会看不见（判成"无漂移"）。这是这条路的固有上限，不是配置问题。真要稳，
**对账脚本应当输出表格或 JSON**：表格里把行级判据放在固定的一列（例 `| 租户 | … | 判定 |`
且单元格里写 `✅ 一致` / `❌ 漂移`），JSON 则直接把漂移租户列出来。

**「跑不起来」和「不达标」必须分开**。脚本因为**没有产物**而失败（"先跑 eval 套件
再对拍"）是环境没准备好，不是数据回归 —— 判成「未实测」并说清缺什么；
只有真的解析出指标差异才报红。这条最容易出假阳性。

**按存储类型定判据**，别一律报红：

| 模块碰到的存储 | 判定 |
| --- | --- |
| 只有一个 PG | 未实测 —— 没有派生层可跨存储校对 |
| PG + **派生存储**（向量库 / 对象存储） | fail（除非有对账机制）—— 权威与派生会漂 |
| PG + **旁路存储**（Redis / 队列） | warn —— 确认它不是权威数据 |

**别对不懂的东西给结论**：识别不出源码文件 ⇒ 退出码 2 + 说清原因（不要输出一堆
关于"空"的 ✓）。Rust / Go 模块目前识别不出来 ⇒ 同样退出码 2 + 说清"当前只实现了
TS/JS/Python"。一个满屏 ✓ 但其实什么都没测的报告，比报错更糟。

**Python 工程**（pytest 系）也判：

- 覆盖率用 `pytest --cov=<包> --cov-report=json`（coverage.py 的合并是确定的 ⇒ 一次就够）。
- **仓库自己的闸门优先**：读 `pyproject.toml` 的 `[tool.coverage.report] fail_under`、
  `Makefile` 的覆盖率目标、`tox.ini` 的环境，闸门的退出码即结论 —— 门槛归仓库所有，
  不用通用阈值。
- 导出 = 模块级公开 `def`/`class`。**别把接口与生成码当逻辑**：`Protocol`/`ABC`/`Generic`
  是接口（对应 TS 的 `interface`/`type`）、`.pyi` 与 protobuf/grpc 生成码不是人写的、
  类体里没有任何 `def` 的纯数据类（DTO/响应模型）只是数据形状 —— 这三类都不算
  "待测导出"，否则噪声盖住真缺口。
- **测试文件三种位置都算**：模块目录内 colocated 的 `test_*.py`（Python 的惯例就是把
  测试放在包旁边）、仓库级 `test/` `tests/` `spec/` 下的 `test_*.py` / `*_test.py`。
  漏掉 colocated 那一种会把整类仓库的公开 def/class 全判成"零引用"。

覆盖率同理：单元测试车道和真后端 itest 车道是两条道。只跑单元车道时报
"service.ts 7%"会被误读成"那文件没人测" —— 实际它的覆盖来自 itest 车道。
默认报覆盖率时要把「另有 N 个 itest 用例未计入」说出来，`--include-itest` 才合并算。

## 覆盖率必须是确定的

**同样一条命令跑两次，覆盖率数字必须一样** —— 否则它不能用来判交付。

node 的 `--experimental-test-coverage` 在**用了 `mock.module()` 的项目**里，
跨 worker 合并覆盖率会竞态：实测同一个模块，同一条命令，覆盖率在
7.26% 与 59.45% 之间跳（文件级独立翻转，测试全绿、数字乱跳）。

**优先级：仓库自己的闸门 > 通用并集**。

- 仓库有覆盖率闸门（脚本名在白名单里、命令含 cov、提到该模块）⇒ **驱动它**，判定看它的
  退出码 —— **门槛归仓库所有**。通用阈值在这里是错的：有的仓库把行覆盖 49% 的
  文件明确列为合格，通用阈值（行 80）会把这些文件判红。
  仓库拆闸的原因也写进了它的 AGENTS.md：每闸只测自己那批、只在该批里加载，
  数字才可复现 —— **别拿通用阈值去覆盖仓库的口径**。
- 仓库**没有**闸门 ⇒ 判「未实测：仓库没有覆盖率闸门，缺少判据」，**默认不阻塞**。
  真要一个通用门槛，用 `--min-line-coverage` / `--min-branch-coverage` 显式指定
  （数字由你定，工具不替你猜）。
- 仓库没有闸门但仍要覆盖率数字 ⇒ 逐个测试文件单独跑（各自独立进程 ⇒ 没有合并 ⇒ 确定），
  再取覆盖**并集**（未覆盖行取交集）。并集回答的正是"这行代码有没有被任何
  测试执行过"。分支/函数覆盖率没有区间数据可并 ⇒ 取各次最大值（偏保守）。

**真后端（itest）车道默认不跑**，要 `--include-itest` 才跑：驱动仓库自己的 itest 脚本
（原样跑，它自带 `MEMORY_ITEST=1`、`--test-force-exit`、钉死清单），只在 runner 参数后、
文件参数前插覆盖率参数 ⇒ 一次跑出「用例全绿」+「真后端覆盖率」。两条车道分开报，
别混成一个数。默认不跑是因为它要连 PG + 向量库、慢，而且环境没就绪时会刷一片报错。

**真后端车道也要分「环境没就绪」与「用例真失败」**：换台机器（CI、同事电脑）
没有 Milvus/PG 时，车道会连不上 —— 那是环境问题，不是产品缺陷 ⇒ 判「未实测」，
不进阻塞项。判据看失败块的 `error:` 详情（用例名里没有报错文本）：
`ECONNREFUSED` / `InvalidPassword` / `UNAVAILABLE` / `connection refused` 等。
注意用例名可能带 `# SKIP set MEMORY_ITEST=1 with local Milvus+PG running`
—— 那句就是仓库自己写下的环境前提。

**显式清单优先于 glob**：仓库钉死文件清单是有意的（glob 会把在途文件一起吸
进来，红灯与产品无关）。

## 覆盖率高 ≠ 测试有劲

**覆盖率只说明代码被执行过，不说明断言会失败。** 一个"杀不死缺陷"的测试套件，
覆盖率再高也不说明问题 —— 它测的是"这行代码跑过"，不是"这行代码错了会不会被发现"。

所以另有一条实测判据「**测试能发现缺陷**」：把源码改坏，再跑该模块自己的测试。

- 只改**比较运算符**（`==` / `!=` / `===` / `!==` / `>=` / `<=`），不改常量、不改字符串、
  不改控制流 —— 那些变异容易变成"编译错误"或"改了无关的语义"，测出来的结论不可靠。
  字符串与注释里的运算符不碰。
- 测试红了 ⇒ 变异被**杀死** ⇒ 这套测试能发现这类缺陷；测试还绿 ⇒ **杀不死** ⇒
  测试套件有洞，报告里点名是哪个文件的哪一行。
- 跑在**仓库副本**里（依赖目录软链），**绝不改用户仓库**。
- **默认不跑**（`--mutation-check` 才跑）：它要复制工作区并多次跑测试，很贵。
  不跑时这条判据是「**未实测**」，不是"通过"。
- **不设分数线**：杀不杀得死多少算够，门槛归项目。工具只报事实与位置 ——
  `0 个杀死 ⇒ 阻塞`、`部分存活 ⇒ 待人工确认（列出位置）`、`全部杀死 ⇒ 通过`
  （并注明"样本有限 ⇒ 不等于这套测试够强"）。
- **环境没就绪 ≠ 杀死了**（同「跑不起来 ≠ 不达标」那条）：测试因为连不上中间件而红，
  或者 runner 的输出认不出用例名 ⇒ 那个变异点**判不了**（既不算杀死，也不算存活）。
  只看退出码的话，环境错误会被算成"杀死了" —— 一个专测"测试有没有劲"的工具
  自己假绿，比没有这条判据更糟。

## 判交付看生产租户

测试用例常**刻意**造出失败态：注入镜像失败、直接插库塞配额占位。这些不是
数据漂移，是夹具状态。**把它们算成阻塞项 = 假阳性**。

| 租户 | 漂移怎么算 |
| --- | --- |
| 生产租户 | **fail** —— 阻塞交付 |
| 测试租户（名字像 itest-/memtest-/mock-/eval-…，或 `--test-tenant` 声明的） | warn —— 信息，不是阻塞 |

实测（一个向量记忆模块）：生产租户 ✅ 一致；两个测试租户分别有 50 行和 4 行
没有向量 —— 前者是测试用例**直接 DB insert** 的配额占位，后者是**注入镜像失败**
造出来的 —— 两个都不是缺陷。按租户口径判之后，这条判据才准。
完整案例见 [examples/cross-store-reconciliation.md](../examples/cross-store-reconciliation.md)。

## 「跑不起来」和「不达标」必须分开

脚本因为**没有产物**而失败（"先跑 eval 套件再对拍"）是环境没准备好，不是数据
回归 —— 判成 skipped 并说清缺什么；只有真的解析出指标差异才报红。

pytest 的 `ERROR`（fixture/环境没就绪，例：连不上 PG）与 `FAILED`（断言没过）
同理：**只有 FAILED 才是"测试没绿"**。这条最容易出假阳性。

## 输出契约：证据清单，不是裁决

报告按**证据类别**分节，不是一张平铺的 ✓/✗ 表：

| 节 | 里面是什么 |
| --- | --- |
| 已实测 | 真跑出来的（测试、覆盖率闸门、对账脚本、基线对拍） |
| 静态信号 | 源码扫描与词频分析得出的（测试卫生、不过度抽象、重复造轮子、依赖清单、oracle 独立性）—— **永远不能单独支撑「通过」** |
| 未实测 | 没测到、判不了的（○） |
| 本工具不判定 | 需求是否被正确理解 · 产品行为 · 性能 · 安全 · 可用性 · 运维就绪 |

结论是三档：**N 项阻塞 · M 项待人工确认 · K 项无信号**。

**为什么不是「能不能交付」**：工具掌握的是 14 条机械判据的实测状态，不是这个模块的
交付裁决 —— 中间那层推理（需求对不对、性能、运维）没有写在任何地方。输出证据清单，
决策留给有职责的人。

**退出码**：有阻塞项，或关键判据（测试是否绿）没测到 ⇒ 1；否则 0。
零测试的仓库在 CI 里必须拿到红灯 —— 那正是"没有测试就别说能交付"。

## 测试要自己收场

**测试往共享库里造的数据不清理 ⇒ 下一个测试看到的是别人的残留。**
（一个向量记忆模块的测试租户就是这个形状：50 行配额占位留在库里。）

判据：测试文件有写库动作，却没有清场动作（收场钩子里没有 delete/truncate/
drop）⇒ 报出来。**只在 `before` 钩子清理**只能保证"不跨轮累积"，跑完仍留
最后一轮 —— 那也是残留。

注意：有些用例是**故意**留着的（"本文件产出的 PG 行 + 向量是人工核对的交付物"）。
这类要报给人看，由人判断，不自动清。

## 等结果，不要固定等待

`sleep(1500)`、`asyncio.sleep(2)` 这类固定等待是 flaky 的来源（同样代码两次跑
出不同结论）。要等的是**结果**：等条件成立，别等时间。

## 写库的测试要自己收场（或者声明它不写库）

「测试卫生」这条判据看两件事：固定等待（flaky 源）与**写库不留清理**（残留源）。
共享库里留下的残留会让下一个测试看到别人的数据，所以写库的测试必须自己收场
（`after` 钩子清干净）。

但有一类测试**确实不写库**：拿假 tx / 内存库跑的单元测试 —— 它没有真库可留残留。
这种**要显式声明**，不要靠加一个空的 `after()` 钩子骗过正则：

```ts
/* attest:no-db-writes reason="假 tx 每个用例重建，不写真库" */
```

- 标记写在**那个测试文件里**，理由**必填**（缺理由 ⇒ 报红）。
- 声明过的文件不再被报「不清理的写库测试」，而且**标记与理由会进报告**
  （文本报告与 `--json` 里都看得见）⇒ 可评审、可追责。
- 固定等待**不豁免**：声明了不写库，该文件里的 `sleep(1500)` 照样被报出来。

为什么不用启发式（看有没有 `mock.module` 掉 db 层之类的）来猜：写库动作本来就只是
**文本**上看出来的，"这个文件其实不写库"只有作者知道 —— 猜会猜错，而且猜出来的
豁免藏在报告里没人看见。判定点那边的豁免（`attest:waive`）就是这么做的：
理由必填、缺了就是错。

## 其余三条（靠人读，不硬编成检查）

- **别测实现细节**：钉的是**行为/不变式**，不是某个组件、某个 DOM 结构。
  用户要的是"能生成上个月的报表"，不是"日期选择器是 Material UI"。
- **断言要具体**："报表看起来对"是让执行者猜。"报表包含这 12 条任务记录，
  不多不少"才是断言。断言要独立取期望值（从接口/库里读），别用被测对象自己的
  输出当期望值。
- **失败要能定位**：用例名要描述**行为**（"月度报表包含工作区的已完成任务"
  而不是 "reports test"）；失败信息要带上期望值与实际值。

## 与 `ai-testing-system` 的关系

- `ai-testing-system` 管**项目级**：成熟度清单、工具矩阵、门禁分层、审计。
- 本 skill 管**需求级**：一个需求的测试工具集长什么样、每条契约钉在哪。

项目先跑 `testkit-audit` 看缺哪些车道，需求再跑本 skill 规划这一条需求的落点。

## 测试包的四性

`check` 还会检查计划钉到的测试文件本身：

| 性 | 检查 | 级别 |
| --- | --- | --- |
| 严谨 | 测试文件里没有断言（覆盖率剧场） | 报红 |
| 逻辑 | 文件头没声明钉了哪些不变量 | 提醒 |
| 复用 | 测试里的助手与仓库已有导出重名 | 提醒 |
| 扩展 | 同一文件里多个用例结构雷同（该参数化） | 提醒 |
