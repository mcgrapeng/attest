# 工作流：线A 每一步怎么写

从需求到计划的每一步：写什么、写成什么样、哪些写法会被判红。

## 跑法

```bash
# 1. 生成计划骨架（扫目标模块的已有 helper + 项目自己的测试车道）
python3 "$SKILL_DIR/scripts/req_plan.py new <feature> \
  --repo <项目根> --module <子路径> [--module <子路径>...]

# 2. 填完不变式与矩阵后，核对计划 vs 代码实况
python3 "$SKILL_DIR/scripts/req_plan.py check <计划文件> --repo <项目根>

# 3.（可选）把模块级维度表升级成判定点粒度，再分批填归属
python3 "$SKILL_DIR/scripts/req_plan.py upgrade <计划文件> --repo <项目根> \
  --module <子路径>
python3 "$SKILL_DIR/scripts/req_plan.py assign <计划文件> --repo <项目根> \
  [--limit 30]
```

计划落到 `docs/<feature>-test-plan.md`（入库、可评审）。`check` 有错误时退出码 1。

**`new` 默认不覆盖**：同名计划已存在时直接报错退出（退出码 1），文件原样保留。
要覆盖加 `--force`；想保留就换 `--out <别的路径>`。仓库没有 `docs/` 目录时会
自动建一个。

**`check` 强制两节**：不变式清单、覆盖矩阵（缺任一 ⇒ 报红）。复用表**有才查**
（不写不报错；写了"复用 XXX"却指不到真实文件 ⇒ 报红）。测试车道**会校验但只给提醒**
（不报红、不影响退出码）。

**跨存储时才校验**两节：数据一致性、约束（不引入中间件）。**触发条件是"有没有写
这两节"**，不是"表里有没有数据行" —— 写成散文、不写表格，都照样校验。写了这节
却没数据行 ⇒ 报红（没有跨存储就删掉整节）。

`new` 也按这个口径生成：模块只碰**一种**存储时**不生成**这两节（省得新计划一出生
就带着两条红），碰**两种以上**才生成。所以单存储模块的计划里找不到这两节是正常的。

一致性节按**表形状**也认（多列且含"权威源 / 镜像 / 派生 / 一致性怎么验"这类列），
所以标题叫 `## 跨存储核对` 也认得出来。

缺权威源、缺镜像说明、缺一致性落点、同一数据两行、没给替代方案、对账路径没落点、
拿中间件/分布式事务当解法 —— 全都报红。**中间件检查无条件跑**：不写一致性节
也拦不住"用消息队列保证一致"这种写法。否定语境（"本项目不引入消息队列"）不算。

**每张表按自己的表头定归属**，标题只在表头不认识时兜底。所以一个标题里混两节
不会吞表（但会提醒拆开）。表头用词随意（`| 场景 | 测试文件 | 车道 |` 认得）。

计划路径先按**当前目录**解析，找不到再按 `--repo` 根解析；两处都没有才报错
（退出码 1，`读不了计划文件`）。**表格每行都要以 `|` 开头**（GFM 允许省略，
但这里的解析器要求有）。

## 工作流

### 0. 零人工：收到需求就一路走到报告

**不需要人参与。** 完整链条（每步做什么）在 SKILL.md 的
「0. 零人工：收到需求就一路走到报告」一节 —— 那里是入口，agent 先读它；这里不重复抄一遍。

**第 1 步「从需求派生不变式」没有工具能替你做** —— 只能靠读需求：

1. 把需求里每一句「必须 / 不得 / 应该」抽出来 —— 那就是不变式的候选。
2. 需求里每个「如果…就…」都要能落到一条：某个输入 ⇒ 某个结果或某个错误。
3. 反查判定点清单：分支、边界、错误路径、资源上限、状态切换、并发 —— 需求提到的
   每一条路径都要有不变式认领它；`assign` 会把没人认领的高危点列出来。
4. 每条不变式钉到一个**真实存在**的用例（`check` 会校验文件与用例名都存在）。

这一节只补入口没展开的一句：**人不需要参与，但痕迹要留下** —— 第 7 步的「确认」节记的是
agent 的名字与依据（模型的确认也是一条可追溯的记录，不是"没人反对"）。那八项本工具判不了，
由 agent 认领并写明依据（能自己判的判，不能的如实写「需人工评审」）。

### 1. 影响面 + 复用侦察 + 存储清单（跑 `new`）

`new` 会扫出三样东西，先看它们再动手写代码：

- **本模块碰到的存储**：PG 表 / 向量集合 / 对象存储 / KV，带文件:行证据。
  **碰了 2 个以上存储 ⇒ 必须有「数据一致性」一节**（`check` 会强制）。
- **已有能力**：目标模块里扫描得到的**符号**（TS 的
  `export function/const/class/interface/type/enum`、`export {…}`（含
  `export { x } from './y'`）、解构导出、具名 `export default function foo()`；
  Python 的 `def` / `class`；Rust 的 `pub fn/struct/enum/trait/type/const/static`）。
  **写新代码前先在这份清单里找** —— 能调就别抄。这直接对应"防止重复造轮子"。
  扫不到 `export * from` / `export * as ns from` / 匿名 `export default`；
  嵌套解构（`export const { a: { b } } = obj`）整条跳过（同语句里的平级兄弟
  也会一起漏）；测试文件（`*.test.*` / `*.spec.*` / `*.itest.*`）里的符号不收。
  清单里可能混着**未 export** 的符号（普通 `const`、私有 `def`）——
  复用前先确认它是导出的。每模块最多列 40 个。
- **测试车道**：项目自己 `package.json` 里名字像测试的脚本。**车道只读 package.json**
  —— Python / Rust / Go 项目扫不到，会输出"没扫到测试车道脚本"，此时车道得自己填
  （`check` 对不存在的车道只给提醒，不报红、不影响退出码）。
  车道清单从项目读，不硬编码 —— 别自己编一个项目里没有的车道。

### 2. 写不变式清单

每行一条行为契约，格式 `| # | 不变式 | 钉在哪 |`。

**钉写 `测试文件::用例名`** —— 工具会核对该用例**真的存在于那个文件里**。
只写文件（`src/x.test.ts`）会提醒"没指到具体用例"：同一文件里测了别的用例
也算出过。

用例名支持 `describe` 嵌套（写全名 `外层 > 内层` 或只写内层名都行）、
`it.each` / `it.skip` / `it.only` 修饰符、Python `def test_…`、Go `func Test…`。

- 不变式 = **这需求必须永远成立的性质**，不是"功能描述"。"召回超时会降级为空"
  是性质；"实现召回功能" 不是。
- **钉在第三列**（不是最后一列 —— 多一列"备注"时钉仍在第三列）。
- 钉的两级强度：`文件::用例名`（工具核对那个用例**真的存在**）>
  `文件` 或 `文件:行`（都只到文件/行，一律提醒）。行号不额外校验。
- 钉写成 `path/to/file.ts:123`：**路径相对仓库根**；扩展名限
  ts/tsx/js/jsx/mjs/cjs/py/rs/go/java/rb/sh（指向 `.md`/`.yaml`/`.sql`/`.vue`
  会被当成"没有钉"）。**行号只是给人看的，脚本不校验它存在** —— 文件在就行。
  目录当钉一般会被扩展名白名单挡掉（报"没有钉"）；若目录名恰好以白名单扩展名
  结尾（如 `foo.ts/`），存在性检查会放过它。
- 不变式行可以三列（`# | 不变式 | 钉在哪`，钉在**第三列**），也可以两列
  （`不变式 | 钉在哪`，钉在**第二列**）。两列行若第二列不是钉路径 ⇒ 报"没有钉"。
- **编号**可以是字母开头（`I1` / `INV-2` / `inv-2`），也可以是纯数字或 `#3`；
  实在认不出会标成"第 N 行"，照样检查，不会静默漏掉。
- 没钉的不变式是未完成的。

### 3. 写覆盖矩阵

每行一个**关键流程**，列出测试落点。

关键流程 = 代码流程的每一个关键细节。只测主干的矩阵不算覆盖 —— 边界、错误路径、
并发、重试、降级、跨租户隔离，各占一行。

- 落点写在**第 2 列**，每行都要有。**落点要是测试文件**（`*.test.*` / `*.spec.*` /
  `*.itest.*`）；指向源文件 ⇒ 提醒（测试命名不合常规时会这样）。
- **描述列里提到的文件名不算落点** —— 落点列空着就是没测。
- 车道列填项目里的车道（`service#test:e2e` 或裸名）。中文描述（"单测"）跳过不查。

### 4. 核心逻辑细节（每个维度都要答）

"测出核心逻辑的细节"落到这张表上。

**哪些维度适用由代码特征推导**，不是固定清单 —— 固定清单会逼着人给无关的维度填
「不适用」，噪声盖住真缺口：

| 维度 | 触发条件（目标模块里出现） |
| --- | --- |
| 边界 | 长度/上下界比较、clamp、MAX_ 常量 |
| 错误路径 | throw / reject / catch / 错误类型 |
| 并发 | Promise.all / 全局状态 / 定时器 / 循环内 await |
| 重试 | retry / backoff / attempts / maxRetries |
| 幂等 | 去重 / 唯一约束 / onConflict / 指纹 |
| 降级/超时 | catch / timeout / AbortSignal / 降级返回 |
| 跨租户隔离 | tenant / orgId / withTenant / RLS |
| 权限 | authorize / permission / grant / role / accessLevel |
| 资源上限 | quota / rateLimit / budget / maxActive |
| 数据对账 | 目标模块同时碰 ≥2 个存储 |

`new` 生成的表里每行都带**触发证据**（哪个文件哪一行触发的），可以核对。
不适用这个需求的维度**根本不会出现**。

计划里可以补：`本需求额外涉及：资源上限、审计留痕`（这些维度也要答）。

### 4b. 判定点归属（v2 计划：升级后的那张表）

`upgrade` 把上面这张模块级维度表换成**判定点粒度**的表，一行一个代码里真正要选的
分支/边界/错误路径：

```bash
python3 "$SKILL_DIR/scripts/req_plan.py upgrade <计划文件> --repo <项目根> \
  [--module <子路径>...]
```

升级后表是六列：`| 维度 | DP ID | 判定点 | 归属的不变式 | 落点（文件::用例名） | 豁免理由 |`。
前两列机器填好（DP ID 与判定点），**后三列要人来判断**：这条判定点归属哪条不变式、
钉到哪个用例，或者写明为什么豁免。

**两条判据口径不一样，别混**

| 判据 | 强制范围 | 一个模块的量级 |
| --- | --- | --- |
| `readiness.py` 的「应有判定点覆盖到位」 | 只有高危四类（错误路径 / 资源上限 / 状态 / 丢弃，即 error-path、resource、state、drop）报红；常规判定点（分支、边界、并发）只计数 | 高危通常一百多条 |
| `req_plan.py check` | **每一条**判定点都要有落点或豁免理由，常规判定点也报红 | 全模块多少条就是多少行 |

所以顺序是：先把高危那批填完，`readiness` 那条判据就绿了；`check` 想全绿，还得把常规那批也逐条填上 —— 那是另一个量级的工时，要不要做是项目自己的取舍。

**三列各填什么**

| 列 | 填什么 |
| --- | --- |
| 归属的不变式 | 不变式清单里真实存在的编号（`I1`、`I2`…）。认领一条就必须给落点 |
| 落点（文件::用例名） | 钉到**真实存在**的用例：`service/src/agent-memory/lifecycle.itest.ts::某条用例`。只写文件会被提醒 |
| 豁免理由 | 认领不了时的出路：写清楚这个判定点为什么不用测。「不适用」三个字会被提醒 |

**另一种豁免：这条不变式不需要判定点认领**

`不变式有判定点` 判据查的是另一头 ——「每条不变式有没有判定点认领它」。
有些不变式**天然**没有认领者：复合不变式（如「跨池同文本合法共存」——
同一条文本在不同池各自成立，不是一个判定点）在判定点粒度下没有对应的 DP。
这时在计划正文写一条注释（理由必填；指向空气、或只写「不适用」都会被拒）：

```html
<!-- attest:invariant-exempt I3 reason="跨池同文本合法共存：两个池各自成立，不是同一个不变式" -->
```

判据认这个出口，但**豁免会出现在报告里**（不静默）；没有理由的、或理由太笼统的，
仍按「没有判定点认领」报 warn。

**用 `assign` 分批填，别手改表格**

上千行 markdown 表格手改既慢又容易错。`assign` 把填表变成一个可分批、可校验、
可增量提交的循环：

```bash
# 1. 拉待填清单（JSONL，一行一个判定点；高危在前）
python3 "$SKILL_DIR/scripts/req_plan.py assign <计划文件> --repo <项目根> \
  [--kinds drop,error-path,resource,state] [--offset 0] [--limit 30]

# 2. 回答写进 JSONL，一行一个：
#    {"dp_id":"…（原样抄回来）","invariant":"I3","pin":"path/to/x.itest.ts::用例名"}
#    或 {"dp_id":"…","waiver":"为什么这个判定点不用测"}

# 3. 写回：校验不过的不写，报出原因
python3 "$SKILL_DIR/scripts/req_plan.py assign <计划文件> --repo <项目根> \
  --apply answers.jsonl

# 4. 看缺口还剩几条
python3 "$SKILL_DIR/scripts/req_plan.py check <计划文件> --repo <项目根>
```

清单第一行是元数据：计划里全部不变式的编号与描述（认领时要用）、
待填总数、高危类型、答案格式。之后每行给 DP ID、类型、维度、源码那一句、
以及**候选测试文件**（同目录下源码里提到这个符号的测试文件）—— 用例名从候选
文件里读，别编。

`--apply` 会挡住四类错：归属的不变式不在清单里、豁免理由太笼统
（只有「不适用」这种）、落点文件不存在、落点用例在文件里不存在（报错时会把
该文件真实存在的用例名列出来）。被挡下的不写盘，其余照写。

填完跑 `check`：高危缺口会一条一条往下掉，没填的会继续报红。
**别为了让 `check` 过而改钉** —— 钉该指哪就指哪。

每个维度**要么有测试落点，要么写「不适用」+理由**。默默跳过 = 没测到
（`check` 会提醒哪些维度没考虑到）。

### 5. 新建能力（先论证不能复用）

新写的抽象/工具列这里，三列：能力 / 为什么不复用现成的 / 调用点。

- **符号全仓已存在** ⇒ 报红：直接复用，别再造一个。
- **调用点 ≤1** ⇒ 提醒：规则之三 —— 抽象要等第三个用例才抽，一个调用点先内联。
- 没写清楚为什么不能复用 ⇒ 提醒。

这是"不过度设计"和"不重复造轮子"的兜底。

### 6. 数据一致性（跨存储才写）

**先看计划里的「本模块碰到的存储」** —— 那是工具扫出来的，带文件:行证据。
碰了 **2 个以上存储**（PG / 向量 / 对象存储 / KV）⇒ **必须写这一节**，否则报红：
两个存储的数据会漂，而漂了没人发现。

表格式：`| 数据 | 权威源 | 镜像/派生 | 一致性怎么验（钉） |`。

- **权威源要单一。** 一份数据只有一个权威，其余都是派生。同一份数据列两行 ⇒ 报红
  （大小写/空格差异也算同一份）。
- 权威源、镜像/派生（没有就写"无"）都不能空。
- 第四列必须是**具体测试文件** —— "一致性怎么验"不是断言，是测试落点。
- **没有跨存储就删掉整节**（留一张空表会被判红）。

校对要覆盖三件事（对账/修复路径必须被测到）：掉的数据能补、重复的不产生、
跨租户的不误删。项目里已有对账机制就复用它，别另写一套
（一个真实案例见 SKILL.md 的 references 表里的 cross-store-reconciliation.md）。

**仓库里没有对账机制？让工具生成骨架：**

```bash
python3 "$SKILL_DIR/scripts/req_plan.py reconcile <计划文件> --repo <根> \
  [--out scripts/reconcile-<模块>.ts]
```

它按这一节的每一行生成一份对账脚本：表名与集合名从计划里抽好，计划写明
「表.列」的那一列直接填成要比对的正文列，其余（主键列、镜像字段名、租户列）
留成 `<待填>`。**填完之前脚本拒绝运行**（启动时扫自己有没有 `<待填`，有就打印
缺哪几项并退出非零）—— 宁可红，不可静默当成「没有漂移」。

生成物的名字里保持有 `reconcile`，`readiness` 就会自动认出它（脚本名含
reconcile + 正文提到本模块的表）⇒ 下一轮验收会**真跑**它，漂移随即进报告。

### 7. 约束：不引入中间件

跨存储一致性的解法在本项目里长什么样（**不引入额外的协调组件**）。

已知的通用形状是 **单权威 + 镜像 + 对账**：

```
写 ──▶ 权威库（PG）────镜像────▶ 派生库（向量库）
              │                      │
              └────── 对账修复 ◀──────┘
```

不引入中间件也能拿到一致性，代价是要写对账与修复路径 —— 那部分**必须被测到**
（掉的数据能补、重复的不产生、跨租户的不误删）。

所以这一节要写两样：

1. 替代方案正文（谁是权威、派生出哪、怎么对账修复）
2. 一行「对账/修复路径的测试落点：src/x.test.ts」

写「用某个消息队列保证最终一致」而不给替代方案 ⇒ **报红**：本项目不引入中间件。
（注意别在计划正文里把这些组件名当成"我们要避开的"写出来 —— 会被当成
"用了中间件"；要表达"不引入"，写替代方案本身就够了。）

### 8. 生成测试工具包（`scaffold`）

```bash
python3 "$SKILL_DIR/scripts/req_plan.py scaffold \
  <计划文件> --repo <项目根> [--out-dir <生成根>]
```

工具会**先认出这个仓库的测试约定**（框架 / 断言风格 / 单元测试位置 / e2e 目录 /
夹具层 / 已有夹具清单），再按约定生成：

- 落点文件**不存在** ⇒ 生成骨架：文件头（钉了哪几条不变量）+ `describe`/`it`
  结构（用例名直接来自计划）+ 断言处留 TODO。
- 落点文件**已存在** ⇒ **不碰它**，只列出「这个文件要加哪几个用例」。

生成的骨架带 TODO —— 断言要有人填。**工具不知道期望值，但读过需求的 agent 知道** ⇒
零人工流程里由 agent 填（`scaffold` 只负责把用例结构与名字写出来）。期望值要**独立
取**（从接口/库里读，或从需求原文推），别拿被测对象自己的输出去当期望值。

### 9. 跑 `check`

```bash
python3 "$SKILL_DIR/scripts/req_plan.py check docs/<feature>-test-plan.md --repo <根>
```

报红类（这些退出码 1）：

| 报红 | 含义 |
| --- | --- |
| 钉指向的文件不存在 | 文件改名了，或这条不变式是编的 |
| 钉的用例在文件里不存在 | 钉错了用例名，或测的是别的用例 |
| 落点的用例在文件里不存在 | 矩阵写错了用例名 |
| 不变式没有钉 | 这条没测（含漏了钉列：两列行的第二列不是钉路径） |
| 矩阵引用了不存在的文件 | 测试还没写，或路径写错 |
| 矩阵这一行没有测试落点 | 流程写了但落点列空着 |
| 没找到不变式表 / 覆盖矩阵 | 少了一节，结构不完整 |
| 复用表引用了不存在的文件 | 声称复用的东西没有 |
| 数据一致性缺权威源 / 缺镜像 / 缺落点 / 同一数据两行 / 数据名为空 | 跨存储的一致性没法核 |
| 目标模块同时碰了 2 个以上存储，却没有一致性校对 | 两个存储的数据会漂 |
| 一致性落点指向的文件不存在 | 对账/一致性测试还没写 |
| 约束缺替代方案 / 缺对账落点 / 对账落点不存在 | 本项目不引入中间件 |
| 拿中间件/分布式事务当解法 | 改成「单权威 + 镜像 + 对账」 |
| 核心逻辑细节某个维度没有落点 | 这个维度没测到 |
| 新建能力的符号全仓已存在 | 重复造轮子，直接复用 |

提醒（不阻塞退出码，但必须处理）：车道不在项目里（编的车道）、落点不是测试文件
（测试命名不合常规）、一个标题里混了两节、没考虑到的核心逻辑维度、
新建能力没论证为什么不复用、调用点 ≤1（规则之三）、
**钉只到文件没指到用例**、**有没用例没有对应的不变式**（测试多余 or 漏了不变式）—— 范围是不变式钉过的文件 ∪ 矩阵落点文件。

复用表**只有含「复用 / 已有 / reuse / existing」字样的行**才会被校验。

**红的必须清掉才算完。** 不要改计划里的钉来骗过检查 —— 钉该指哪就指哪。
